Extension architecture concept · 2026-08-06

Let focused tools join a component inspection—without joining Desy core.

Introduce a typed detail-extension boundary rendered inside the inspector for one registered component. Prove it with desy_agent_annotations: a small comment composer that hands a component-scoped annotation to a consumer-supplied asynchronous callback.

Impact 4/5 Complexity 3/5 Yield 4/5 Recommended: narrow build

Summary decision

Build the boundary and one proving extension. Add DesyDetailExtension alongside—not inside and not as a replacement for—DesyWorkspaceExtension. DesyBenchApp receives an immutable list of detail extensions, validates their IDs in the existing shared namespace, and lets the detail inspector render matching extensions in registration order.

The annotation extension emits one rich, immutable submission object through Future<DesyAgentAnnotationReceipt> Function(DesyAgentAnnotation). A macOS consumer may write that object to a repository file; a hosted web consumer may pass it to a server-side GitHub issue function. Neither behavior belongs in desy_bench.

Why this exists

User value

A designer or developer can record an actionable observation while the exact component is open. The receiving agent gets stable component identity and source context rather than an ungrounded comment copied from elsewhere.

Product value

The sample tests whether Desy's typed extension model works below the route level. If this seam is sound, future focused tools—review notes, source links, validation findings—can attach to details without inflating the registry contract or workbench core.

Evidence and constraints

Observed todayArchitectural consequence
There is one public extension type, DesyWorkspaceExtension, and it owns a routed screen.Detail content needs a parallel placement-specific declaration; overloading a screen extension would mix routing and inspector concerns.
The detail inspector is one Desy-owned ListView containing instances, knobs, and empty state.The host can add one extension region after core controls without a new route or a second panel system.
DesyBenchApp already validates extension IDs against the registry's shared stable-ID space.Detail extension IDs join that same validation input; no second registry or index is needed.
The workbench session already exposes the immutable registry and active theme to workspace extensions.A detail context should repeat that explicit read-only pattern and add only the current resolved component target.
The first release is local-first and has no backend or account model.GitHub authentication and file persistence stay behind consumer callbacks. A browser must never contain a repository token.

Scope

In the first slice

  • A public, immutable DesyDetailExtension declaration with stable ID, name, optional description, applicability method, and widget builder.
  • A read-only DesyDetailExtensionContext containing the active registry, active theme, resolved entry, and non-null component.
  • A detailExtensions argument on DesyBenchApp, internal session propagation, shared ID validation, deterministic registration-order rendering, and a bounded fallback for synchronous appliesTo or declaration build failures. Errors thrown later by returned widgets follow Flutter's normal element reporting and ErrorWidget behavior.
  • An optional packages/desy_agent_annotations package containing the section UI, typed submission/receipt objects, and required async callback.
  • A sample registration showing a macOS repository-file sink and the seam through which a hosted web app supplies a GitHub-issue function.

Non-goals

  • No annotation database, cloud sync, user identity, account system, history browser, or Desy-owned GitHub authentication.
  • No mutation of DesyRegistry, component declarations, routes, knobs, or preview state.
  • No callback or comment serialized into a future screen manifest.
  • No generalized plugin lifecycle, dependency injection container, event bus, arbitrary inspector slot system, or extension-to-extension communication.
  • No detail extensions for colors, typography, or other primitives until the component-only seam is proven.

Architecture

Consumer DesyRegistry+ immutable detail extensions→ DesyBenchApp validation→ component detail route→ Desy-owned extension region→ extension-owned section + local state→ consumer async sink

Recommended public shape

abstract class DesyDetailExtension {
  const DesyDetailExtension();

  String get id;
  String get name;
  String? get description => null;

  bool appliesTo(DesyDetailExtensionContext context) => true;

  Widget build(
    BuildContext context,
    DesyDetailExtensionContext extension,
  );
}

@immutable
class DesyDetailExtensionContext {
  const DesyDetailExtensionContext({
    required this.registry,
    required this.activeTheme,
    required this.entry,
    required this.component,
  });

  final DesyRegistry registry;
  final DesyTheme activeTheme;
  final DesyRegistryEntry entry;
  final DesyComponent component;
}

The base class supports both a convenience builder factory and custom subtypes, matching the existing workspace extension ergonomics. The context deliberately excludes the internal session, router, mutable knob map, and panel controls. Future context fields must be explicit, read-only domain objects—not handles to hidden workbench state.

Ordering rule: use registration order in v1. Do not add priorities, before/after constraints, or named slots until two real extensions demonstrate the need.

desy_agent_annotations proving extension

Interaction

  1. The component detail opens and shows an Agent annotation section after controls.
  2. The user writes a plain-text comment in DesyTextField. The submit action is disabled for blank input and while a request is active.
  3. The extension snapshots component identity, optional source path, folder path, active theme ID, comment, and creation time into one immutable DesyAgentAnnotation.
  4. The supplied callback runs. Success returns a receipt such as a local file path or GitHub issue URL; failure remains editable and can be retried.
  5. On success the draft clears only after the receipt is available.

Accessibility

Use the central native-backed DesyTextField, an explicit label and hint, keyboard submission that does not steal newline entry, a semantic progress announcement, and text—not color alone—for success or failure.

Callback contract

typedef DesyAgentAnnotationSubmit =
    Future<DesyAgentAnnotationReceipt> Function(
      DesyAgentAnnotation annotation,
    );

@immutable
class DesyAgentAnnotation {
  final String componentId;
  final String componentName;
  final List<String> folderIds;
  final String? sourcePath;
  final String activeThemeId;
  final String comment;
  final DateTime createdAt;
}

@immutable
class DesyAgentAnnotationReceipt {
  final String message;
  final Uri? location;
}

The model is deliberately component-scoped. It does not include widget objects, callback references, raw knob values, agent prompts, GitHub fields, or local filesystem paths chosen by Desy. If a sink needs repository or issue metadata, the consumer closes over that configuration when constructing the callback.

Platform sinks stay outside core

macOS: repository file

The sample consumer supplies a callback backed by dart:io. It writes UTF-8 Markdown beneath a consumer-chosen repository directory such as .desy/agent_annotations/, using a collision-safe filename and returning the file URI in the receipt. Conditional imports keep IO code out of web builds.

Hosted web: GitHub issue function

The hosted app supplies a callback that invokes its authenticated server function and maps the response to a receipt. Repository, labels, title policy, deduplication, authentication, and rate-limit handling are deployment concerns. Never place a GitHub token or issue-creation secret in compiled Flutter web code.

The extension package is therefore platform-neutral: it depends on Flutter and desy_bench, not dart:io, GitHub SDKs, or a backend client.

Acceptance criteria

  • A minimal registry remains useful with detailExtensions: const []; current workspace-extension registrations continue to compile unchanged.
  • A registered detail extension appears only on component detail routes, never creates navigation, and receives the same registry object used by the workbench.
  • Duplicate IDs across registry declarations, workspace extensions, and detail extensions fail at startup.
  • Two detail extensions render once each in registration order and keep independent widget state.
  • Changing the active theme rebuilds the context without replacing the registry or clearing an in-progress annotation draft.
  • Blank submissions are rejected locally; one active callback prevents duplicate submissions; failure is visible and retryable; success exposes the returned receipt.
  • The annotation package compiles for macOS and web without importing IO or credentials; the macOS sample sink writes a real file in a temporary-directory test.
  • Keyboard navigation, system text scaling, semantics, and task check pass.

Open questions

  1. Draft lifetime: is route-local state sufficient, or must unsent text survive switching between components? Recommendation: route-local for the proving slice; add an explicit extension controller only after observed loss.
  2. Preview specificity: should an annotation include selected scenario/instance IDs? Recommendation: defer. The first semantic target is the component declaration; raw knob values may contain runtime widget choices and should not leak into a submission model.
  3. Local file convention: should the sample choose .desy/agent_annotations/ or require a path? Recommendation: callback construction chooses the repository root and directory; the extension knows neither.
  4. Receipt actions: should Desy open returned locations? Recommendation: render/copy the receipt first; external launching is a separate platform capability.

Decision: do the narrow slice. Stop after the typed boundary, annotation package, macOS file callback example, and hosted-function seam. Do not build cloud storage, direct GitHub OAuth, cross-component draft persistence, or a general inspector plugin framework in the same feature.

Principle gates: one declared system; consumer-owned, tool-enabled; local first; Forui scaffold; typed object-shaped interfaces; progressive disclosure; typed workspace boundaries.
