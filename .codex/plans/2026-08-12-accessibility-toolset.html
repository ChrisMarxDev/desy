One scoped accessibility toolset for every real Desy preview

Turn the current semantics overlay into a trustworthy review and verification toolset: show what assistive technology receives, apply practical environment stress tests, and make deterministic checks available in component tests—without treating Desy chrome as consumer UI or creating a parallel registry.

Package owner: desy_benchNo backend or persistenceOpt-in, preview-scopedPlan requires approval
Current recommendation

Keep Flutter’s SemanticsDebugger as the label-and-bounds overlay; add Desy’s own diagnostic receipt and test harness. Evaluate accessibility_tools as a development-only optional extension afterwards, rather than placing its global app wrapper in the core workbench.

1. Goal and scope

In scope

  • A compact consumer-preview toolbar/card that enables a semantics label-and-region overlay.
  • A structured, readable “semantics receipt” of labels, roles, states, actions, bounds, and warnings for the selected preview root.
  • Named environment presets: default, large text, RTL, bold text, high contrast, reduced motion, plus reset.
  • A test helper that checks consumer components against Flutter’s label, tap-target, and contrast guidelines in declared preview scenarios.
  • Optional debug-only diagnostics such as missing labels and tap areas.

Out of scope

  • No claim that a tool proves full WCAG conformance.
  • No mutation of registry declarations or production widgets.
  • No inspection of Desy scaffold/nav/control semantics.
  • No remote service, account, accessibility audit storage, or automatic fix.
  • No custom tree inspector that depends on retained live Element or RenderObject references.

4. Logic and data flow

1 · RegistrySelected entry resolves the consumer’s real builder.
2 · SessionEphemeral preview accessibility state selects an environment and visual mode.
3 · ScopeOnly the consumer preview receives MediaQuery/Directionality; the visual overlay is clipped to the artboard.
4 · Audit seamA feasibility spike proves a true preview-root snapshot before a receipt is promised.
5 · VerifyTests run Flutter guidelines against declared component/scenario fixtures.
  1. The registry remains the only source of components, themes, scenarios, and stable IDs.
  2. The detail screen asks the session for its preview state and composes the existing real-widget preview inside DesyPreviewAccessibilityScope.
  3. Overlay mode is immediate and reversible; it never changes the actual consumer widget builder or its registry contract. It is called “Visualize semantics”, not “inspect” or “audit”.
  4. Receipt generation is phase 2 and has an explicit feasibility gate: if Flutter cannot expose an explicit preview-root snapshot with accurate artboard coordinates, the tool reports “unavailable” rather than falling back to view-wide/Desy-chrome evidence.
  5. Test helpers give teams a repeatable baseline. A component can run default and declared accessibility scenarios without any runtime inspection surface.

7. Backend and database changes

None. This is local-first, ephemeral workbench state plus repository-native tests. There are no tables, migrations, network APIs, accounts, generated production code, or persisted audit results.

9. Risks and seams to watch

RiskMitigation
Overlay is mistaken for an audit or claimed to be preview-root scoped.Use explicit language: “visualize semantics”. Document that Flutter’s debugger reads the view-wide pipeline and keep any scoped receipt behind a feasibility gate.
accessibility_tools wraps the whole app and reports Desy chrome.Keep it out of core. Prototype it only as an app-root developer aid. Do not present it as consumer-preview evidence.
Diagnostics are noisy across platforms/themes.Start with Flutter’s own guideline matchers in test support, use named scenario contexts, and report platform/preset evidence with each result.
Semantics snapshots become stale during hot reload or stateful interactions.Tag receipts with entry/theme/scenario/generation; clear and ask for explicit re-inspection on mismatch.
Live tree ownership leaks into durable workbench state.Persist only stable IDs and value snapshots. No Element/RenderObject callbacks or opaque framework handles in session/URLs.
