A finite, typed object canvas for Flutter

Create a small reusable package that owns only canvas-bounded object geometry and interaction. It should replace duplicated movement, resize, transform scale, rotation, selection, viewport, snapping, guides, and ephemeral undo/redo in Screenshot Builder and Sketch/Canvas V2 while remaining independent of Desy, image/text domain models, persistence, and editor chrome.

  objectBuilder: (context, object, state) => switch (object.data) {
    ImageElement element => buildImage(element),
    TextElement element => buildText(element),

The widget has no objects, onObjectChanged, or onAction state API. The controller is the sole source of document, selection, history, viewport, and action-event state. The widget only renders that controller and accepts visual builders/policies.

Recommended invariants: size and scale never mean the same thing. Resize modifies real layout constraints. Transform scale modifies the painted footprint after layout. Rotation and scale share an explicit pivot. List order is paint order. Constraints and capabilities resolve from canvas defaults first; an object declares an override only when it differs.

Sensible rendering default without weakening generic data

// Arbitrary host data must explain how it becomes a real widget.
ObjectCanvas<EditorElement>(
  controller: editorController,
  objectBuilder: buildEditorElement,
);

// When the data itself is already a Widget, no builder is necessary.
ObjectCanvas<Widget>.widgets(
  controller: widgetController,
);

A universal default builder cannot safely render an unconstrained T: the package cannot know how an ImageElement, text-style ID, registry ID, or application model becomes a widget. The typed .widgets constructor is the honest zero-boilerplate default, while the generic constructor preserves arbitrary data and real host rendering.

transformScaleChanges geometry.scale; the child keeps its logical layout size and the completed widget is painted larger/smaller around its pivot.Explicit controller mode. Rendering requires an attached and painted ObjectCanvas; otherwise the controller reports a typed not-attached/not-ready error. The captured RepaintBoundary surrounds only the finite stage background and object content. At pixel ratio 1, output pixels equal logical canvas dimensions. File naming, filesystem writes, downloads, and share sheets remain host concerns.

sealed class CanvasAction<T> {
  String get id;
  String get description;
  CanvasActionKind get kind;
}

final class CanvasValuePatch<V> {
  final V before;
  final V after;
}

final class CanvasGeometryPatch {
  final CanvasValuePatch<Offset>? position;
  final CanvasValuePatch<Size>? size;
  final CanvasValuePatch<double>? rotation;
  final CanvasValuePatch<double>? scale;
  final CanvasValuePatch<Alignment>? pivot;

  CanvasObjectGeometry applyTo(CanvasObjectGeometry current);
  CanvasObjectGeometry revertOn(CanvasObjectGeometry current);
}

final class CanvasTransformAction<T> extends CanvasAction<T> {
  final String objectId;
  final CanvasGeometryPatch patch;
  final CanvasTransformKind transform; // move | resize | scale | rotate

  void apply(CanvasActionTarget<T> target);
  void revert(CanvasActionTarget<T> target);
}

// Pointer down: capture `before`.
// Pointer updates: render draft geometry only; do not touch history.
// Pointer up: create and perform exactly one action.
controller.perform(CanvasTransformAction(
  objectId: 'hero-image',
  patch: CanvasGeometryPatch.between(
    gestureStartGeometry,
    finalSnappedGeometry,
  ),
  transform: CanvasTransformKind.resize,
));

CanvasHistory adapts each typed action to one undo.Change. Because ChangeStack.add() executes immediately, gesture frames stay in separate draft state and only pointer-up adds/applies the action. The patch contains exact old/new values only for fields that changed: apply writes each after; revert writes each before. This avoids complete object snapshots and floating-point drift from repeatedly adding/subtracting arithmetic deltas. A no-op patch creates no action. Selection, hover, camera movement, and snap-guide state never enter document history.

Architecture

Host domain
  List<CanvasObject<T>> + objectBuilder(T)
             │
             ▼
ObjectCanvasController<T>  ← programmatic add/remove/select/focus
  ├─ committed document: canvas size + immutable ordered objects
  ├─ view state: selection + camera transform + active transform tool
  ├─ interaction state: active object draft + snap session + guides
  └─ history adapter: CanvasAction<T> ↔ undo.ChangeStack
             │
             ▼
ObjectCanvas<T>
  ├─ viewport adapter (InteractiveViewer + TransformationController first)
  └─ finite stage (clip/background/border)
       ├─ arbitrary object widgets, laid out at geometry.size
       ├─ paint transform: position + pivot + rotation + scale
       └─ overlay: hit region + single/multi-selection frame + legal handles + snap guides
             │
             ▼
CanvasActionEvent<T> stored on controller after commit | undo | redo

Pure geometry seam
  CanvasTransformEngine ─ CanvasSnapEngine ─ CanvasSceneIndex
  No widget data, registry, persistence, file IO, editor panels, or theme dependency

Model layer

Immutable objects, reversible patches, actions, and validation. Geometry stores position, real layout size, radians, positive transform scale, and pivot. Canvas-level defaults provide minimum size and capabilities; nullable per-object policy fields override only true exceptions. Each action stores only its changed fields, with exact old/new values sufficient for deterministic apply/revert.

Controller layer

Owns lifecycle, unique-ID validation, paint order, selection, view state, and history. During a gesture it updates only object-scoped drafts. At gesture end it creates one typed CanvasAction; the history adapter uses undo.ChangeStack to apply, undo, or redo that action through the same document mutation path.

Geometry layer

Pure deterministic operations for local/world transforms, rotated corners, axis-aligned visual bounds, containment, handle deltas, resize versus scale, and snapping. No BuildContext or host data.

Widget layer

Composes Flutter's supported camera/gesture primitives and the selected transform dependency. It renders only inside the canvas and exposes builders for content and visual chrome.

Customization layer

Small interfaces: object builder, selection/handle builder, guide builder, background builder, hit-test delegate, snap strategies, boundary resolver, keyboard/modifier policy. Defaults remain useful.

Consumer adapters

Desy adapters map registry IDs, knobs, images, text styles, artboards, and layouts into host data. None of those types enters the package.

Backend and Database Changes

None planned. This is an in-memory Flutter package. It defines no serialization, files, backend, database, migrations, environment variables, RPCs, authentication, or deployment. Core rendering returns ui.Image/PNG bytes only; host apps own filenames, storage, downloads, sharing, and persistence.

Open Decisions

No product/API decisions remain open for kickoff. Phase 0 remains a verification gate for supported Flutter/dependency composition, not permission to silently replace native gestures or resizing.

#Resolved decisionDefinition
1Package nameobject_canvas; public center is ObjectCanvas, CanvasObject<T>, and ObjectCanvasController<T>.
2State ownershipController-only. ObjectCanvas receives a controller and visual builders/policies; it has no objects, onObjectChanged, or onAction state API.
3Object defaultsCanvas-level minimum size and capabilities apply automatically; an object supplies typed overrides only when exceptional.
4Object renderingArbitrary T requires objectBuilder; ObjectCanvas<Widget>.widgets is the zero-builder convenience.
5Action observationCommit/undo/redo state lives on the controller as lastActionEvent/history; consumers observe the controller rather than wiring widget callbacks.
6History payloadOne completed intention creates one typed action containing reversible field patches with exact old/new values only for changed fields.
7History limitDefault 100 completed document actions, configurable and clearable; history is in-memory and never serialized by V1.
8Resize versus scaleThe controller owns layoutResize versus transformScale mode. Layout resize changes real constraints and reflows the child; transform scale preserves logical size and changes its painted footprint. Host UI switches the mode; a configurable desktop modifier may temporarily invert it.
9Multi-selectionV1 supports shift/toggle and marquee selection plus shared movement. The union hull snaps/moves as one unit and commits one composite action. Resize, scale, and rotation are available only when exactly one object is selected.
10Rotation implementationUse Flutter's native gesture recognizers/input details and package-owned pure pivot/rotated-bounds geometry. Evaluate box_transform only for ordinary layout resize. Do not depend on unreleased upstream rotation or a broad editor package; if supported composition cannot cover rotated resize, stop and document the native/dependency gap before custom resize behavior.
11Rendering boundaryMounted finite-canvas rendering is core: background plus real objects to ui.Image or PNG bytes at explicit pixel ratio, without selection chrome. File naming, filesystem writes, downloads, sharing, and export UI stay host-owned.
