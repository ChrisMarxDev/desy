Implementation plan2026-08-06Desy Bench

A persistent, inspectable system workbench—before a screen builder or agent layer.

Replace the prototype-derived single file with a small state-beacon session layer and focused Forui surfaces. The consumer registry stays authoritative; instances and the temporary canvas only reference it.

Decision needed

Goal and scope

In scope

  • Persistent sidebar, working themes, selectable concise copy.
  • Modular Forui Atlas, detail workspace, resizable preview, knobs, and instances.
  • Searchable widget-instance swap dialog.
  • Temporary component canvas with drag/resize.
  • SimDeck setup, simulator test-drive, tests, and docs.

Not in scope

  • Persistence, source generation, routing, hosted collaboration, or agent skills.
  • A generic visual editor/Figma replacement.
  • Serializing widgets or callbacks into the registry.

Logic and data flow

Consumer DesyRegistry (immutable source of truth)
  -> themes, atoms, components, contracts, named instances
  -> WorkbenchController (session-only Beacons)
       -> active theme / route / entry / knob values / swap query / canvas boxes
  -> Forui root shell (sidebar stays mounted)
       -> Atlas | themes | detail | Components canvas
  -> selected consumer theme wraps only real consumer preview

No UI state mutates the registry. Canvas boxes reference component IDs and disappear
with the controller. A selected component instance resets its declared knobs to its preset.

  • Theme transition crossfades only preview wrapper; Bench chrome is independent.
  • All Desy copy uses a selectable wrapper; consumer preview remains interactive.
  • Detail is title/context → instances → stage → Forui knobs/contract. Resize handles have an explicit drag surface and visible size readout.
  • Widget-slot knob opens a Forui search dialog with a bounded empty state and declared-instance preview.
  • Font Atlas becomes one specimen plus roles—no generic explanatory prose.

Backend and database changes

None. All data is consumer-owned Dart source; instance choices and canvas layout are deliberately ephemeral. No migrations, backend, tables, RLS, cloud tasks, or secrets.

Tests and verification

Risks and seams

  • Forui coverage must be confirmed as modules are written; a missing primitive gets a minimal low-level input inside a Forui surface, never a Material form chrome regression.
  • Selectable Desy text must not intercept consumer preview interaction.
  • Canvas package is a transform utility only—not persistence architecture.
  • Instance IDs must be unique and slot-compatible; missing resolution renders bounded error UI.
  • SimDeck needs a booted simulator and debug app; capture logs/screenshots under /tmp.
