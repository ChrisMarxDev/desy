Performant element and pixel-grid snapping

A private, pure-geometry snapping engine for Desy Bench that gives Figma-like edge and center alignment without making pointer movement depend on widget rebuilds or full-scene scans.

Repository: flutter_design_system_bench Package: desy_bench Status: ready for implementation approval Scope: Sketch canvas
Decision needed

None remaining. The batch-grill defaults were accepted: element snapping outranks grid snapping, snapping is always on, grid size is session-local, and equal-spacing guides are deferred to phase 2.

1. Goal and scope

In scope

  • Always-on element snapping for move and resize.
  • Left/center/right and top/center/bottom anchors, including adjacency such as right-to-left.
  • Always-on configurable pixel grid: presets 1, 2, 4, 8, 12, 16, 24, 32 and custom integer 1–256.
  • Scale-aware 6 screen-pixel acquisition and 10 screen-pixel release hysteresis.
  • Localized smart guides for every collinear target at the winning coordinate.
  • Keyboard movement by one grid unit; Shift moves four units.

Explicitly out of scope

  • Equal-distance and distribution snapping (phase 2).
  • Nested slot-child snapping; only top-level canvas components, layouts, and bezels participate.
  • Registry or manifest persistence for grid settings.
  • A public package in the first pass.
  • Replacing flutter_box_transform.

3. Logic and data flow

1 · BeginSnapshot committed top-level rects and exclude the active node.
2 · IndexCreate three X and three Y anchors per target, then sort each flat array.
3 · ResolveFor each pointer proposal, query only the tolerance windows with binary search.
4 · PaintApply the corrected rect to the local transform controller; repaint node and guides only.
5 · CommitWrite one final rect to the shared node map, clear locks/guides, discard the index.

Hot path per pointer event

  1. Convert 6 screen pixels to canvas units using the current zoom. If an axis is already locked, test its 10-pixel release threshold first.
  2. Derive at most three moving anchors per axis (fewer during an edge resize).
  3. Use lowerBound/upperBound on the sorted axis arrays to inspect only anchors inside the acquisition window. No scan of every canvas node.
  4. Rank candidates by smallest correction, then corresponding edge, adjacency, center, and stable node ID. Resolve X and Y independently.
  5. If no element wins an axis, snap that axis to the grid with constant-time rounding. Element snapping therefore always outranks grid snapping.
  6. Apply resize correction only to active edges. Preserve the opposite edge; for corner resizing, resolve both axes and apply bezel aspect-ratio rules deterministically.
  7. Update the guide notifier only when the winning coordinate/target set changes. Reuse the current result otherwise.
O(n log n)
Once, when a gesture begins, to create sorted anchor arrays.
O(log n + k)
Per axis and moving anchor, where k is only the anchors inside the tolerance window.
O(1)
Grid fallback through arithmetic; changing the grid never rebuilds the element index.
1 commit
Shared canvas state changes once per completed gesture, not once per pointer event.

Why sorted axis arrays first

Snapping asks a one-dimensional nearest-coordinate question independently on X and Y. Flat sorted arrays have less allocation and indirection than an R-tree and produce predictable cache-friendly lookups. A spatial tree is reserved for a later continuous/infinite canvas only if profiling shows candidate density makes k too large.

Repaint and allocation discipline

  • The snap engine receives Rect snapshots, never measures widgets, traverses render objects, or uses global keys.
  • The moving preview and guide overlay sit behind separate RepaintBoundarys. Stationary previews do not repaint during drag.
  • Anchor arrays are flat immutable lists. The session reuses locks and result buffers; guide lists are recreated only when the winning match changes.
  • Grid painting calculates visible line indices and skips minor lines when zoomed out, with one major line every eight cells.
  • Frame-coalesced presentation updates are allowed for labels/guides, but geometry correction itself stays synchronous and local so the pointer never outruns the object.

6. Backend and database

None. This remains local-first and repository-native. Grid settings and snap sessions are ephemeral; no schema, storage, network API, migration, account, or generated production widget code is introduced.

9. Accepted decisions and open decisions

Accepted

  • Private Desy engine first; potential package later.
  • Keep flutter_box_transform; use Fluera only as a source reference.
  • Element beats grid; stable deterministic tie-breaks.
  • 6 px acquire / 10 px release in screen space.
  • Grid defaults to 8 and is always on.
  • Top-level nodes only; keyboard is grid-only.
  • Gesture-start index and end-only shared commit.
  • Distribution/equal spacing is phase 2.

Open

No product decisions block implementation.

One implementation detail is deliberately resolved by profiling: identical-coordinate buckets start as compact lists; a broader spatial index is added only if 10,000-target traces miss budget.

Research basis

No published Dart package is a clean reusable fit. stack_board_plus and similar packages are full boards with grid snapping. fluera_canvas is the closest reference; its GitHub main branch exposes a pure engine, but the API is unpublished and still expects caller-side candidate culling. See the repository note at docs/research/flutter_snap_alignment_packages.md.
