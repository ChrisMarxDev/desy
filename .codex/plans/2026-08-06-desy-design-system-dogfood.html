Implementation planDesy Bench2026-08-06 · Europe/BerlinDraft pending grill

Make Desy’s own design system its most demanding consumer.

Extract Desy-owned foundations and reusable UI into a dedicated Flutter package, make the workbench consume that package, and ship a colocated catalogue app whose single DesyRegistry documents every exported element. Preserve the Harbor sample as the independent consumer proof.

Decisions needed — one batch

Recommended options are selected. These are the choices that materially alter dependencies, public API, or migration scope.

A avoids a cycle and keeps this migration bounded. The colocated example app is the dogfood registry owner.
A keeps the design system free of product workflows while forcing all Desy chrome to use its public components.
A follows Dart workspace conventions while still being a Desy-owned subpackage.
A preserves consumer independence and centralizes the Desy-owned dependency.
A produces truthful usage guidance without turning implementation details into public API.
A lets the extraction land incrementally; deprecations can be scheduled later.
A proves both self-use and consumer neutrality.

Migration phases

1 · Establish boundary

Create package, theme root, tokens, icons, text field, shortcut label, and boundary tests. Add workspace/tasks. Bench still compiles through compatibility exports.

2 · Component layer

Wrap current Forui primitives with intentional Desy APIs. Add widget tests and catalogue entries/instances as each component becomes production-ready.

3 · Workbench migration

Migrate app root, shell, sidebar, Atlas/detail/measures/themes/showcases, canvas, and extension. Remove direct Forui from Desy-owned packages.

4 · Ultimate dogfood

Complete dogfood registry/app, coverage assertion, documentation, manual run, and preservation checks against Harbor.

5 · Harden

Canonical format/analyze/test, web/macOS builds, import-boundary check, and optional publish dry-runs. Update durable context only after decisions land.

Backend and database changes

None planned. The source of truth remains immutable repository-owned Dart code. There are no tables, migrations, RPCs, RLS policies, indexes, jobs, accounts, environment variables, deployments, backfills, or caches. The executable is a local Flutter app.
