Product concept · Flutter

A simpler, AI-forward Widgetbook for designing real Flutter screens.

A structured canvas for defining atoms and components, composing them freely into screens, and deriving a reliable design-system skill from the living system.

atoms-firstFlutter-nativedrag & dropAI-forward

The thesis

Widgetbook is a gallery of widgets. This is a design-system workshop: define the durable primitives once, compose them into UI, and let agents receive the exact component vocabulary they may use.

The mental model

Atoms

Colour, type, spacing, radius, elevation, icon, image, divider, and interaction primitives. These are the hard vocabulary.

Components

Button, field, card, list row, app bar, sheet, navigation, and feedback. Each has explicit, strongly typed slots and variants.

Screens

A freeform canvas for composing components into real responsive flows—without permitting arbitrary styling that escapes the system.

Freeform where it matters; hard rails where drift starts

Open canvas

  • Drag components onto a responsive device canvas.
  • Nest, reorder, duplicate, and bind ordinary sample data.
  • Create app-specific compositions and save them as stories/screens.
  • Switch themes, locales, text scale, and device sizes instantly.

Hard slots and constraints

  • Page shell: app bar, body, bottom actions, navigation.
  • Layout: row, column, stack, scroll, grid, section.
  • Components expose named slots, not arbitrary children everywhere.
  • Spacing, colour, typography, and elevation must select atoms/tokens.

That is the useful middle ground: more fluid than a story catalogue, but deliberately not Figma-in-Flutter. A screen can be arranged freely; its visual language cannot quietly fork.

What the app looks like

Library · Canvas · Inspector

Left: atoms and component library. Centre: phone/tablet/desktop canvas with drag targets and drop zones. Right: selected component’s allowed variants, named slots, token controls, accessibility requirements, and generated Flutter outline.

The key interaction

Drop a PrimaryButton into Page.bottomActions; the inspector allows label, icon, and state—not a random background colour or unapproved corner radius.

Skill generation is a build artifact

The workbench derives one canonical design-system skill from its registry. It contains the complete atom list, component catalogue, slot model, variant matrix, composition rules, examples, and verification commands. Agents do not invent the system; they query and use it.

Atom registry+Component schemas+Saved screens+Rules→design-system/SKILL.md

Later, it can generate smaller skills automatically—checkout-ui includes only the relevant atoms and components, linked to the authoritative system skill.

Recommended first release

Define atoms and components with an intentionally small Dart schema.

2

Compose

Drag components into constrained screen layouts; save and render real Flutter screens.

3

Derive

Export the system skill plus a verification command and source links.

Deliberate boundary

Do not make the first version a general visual-programming environment. The screen builder needs only enough layout freedom to create realistic compositions. Keep app logic, arbitrary CSS-like overrides, Figma sync, and autonomous source edits out of the first loop.

Open questions

  • Should the builder emit a durable Dart screen file, a declarative screen manifest, or both?
  • Which slots are universal enough to standardise in the first layout primitives?
  • How much sample-data binding makes the canvas useful without turning it into an app builder?
  • Should an agent access the registry through generated Markdown only, or a local query tool too?
