Design-system guardrails

Turn the registry into a compiler for design intent.

The agent should receive precise feedback when it chooses an unregistered component, illegal value, raw color, unsupported slot, or inaccessible state.

Impact 5/5Complexity 4/5Risk 3/5

Reason and user value

Instructions like “follow the design system” are too soft. Machine-readable diagnostics let an agent repair its own work and give human reviewers a consistent policy baseline.

Scope

  • Strict validation for Desy manifests and generated A2UI/SDUI surfaces.
  • Rules for registered IDs, knob domains, legal slots, deprecated entries, and required scenarios.
  • Optional Dart analyzer package for consumer-defined policies such as raw colors or direct primitive usage.
  • Human output, SARIF, and stable JSON with suggested registry alternatives.
  • Severity and rule configuration owned by the consumer.

Non-goals

  • No claim to understand arbitrary runtime widget trees statically.
  • No mandatory “Desy widgets only” policy.
  • No auto-fix when semantics are ambiguous.
  • No Forui rule leakage into consumer previews.

Implementation sketch

  1. Define diagnostic codes alongside manifest validation.
  2. Add registry-backed suggestions and deprecation replacements.
  3. Expose desy check and machine-readable output.
  4. Add an opt-in analyzer plugin for a small set of high-confidence source rules.
  5. Feed diagnostics back into the agent skill and annotation loop.

Open questions

  • Which source rules are reliable without false positives?
  • How do consumers declare approved exceptions?
  • Should accessibility rules live here or in scenario verification?
  • How are rules versioned with the registry?

Do or don’t?

Do in layers. Manifest checks are exact and should come first. Dart analysis is valuable only where a consumer can opt into narrow, explainable rules.

Offline concept artifact. No remote assets or runtime dependencies.
