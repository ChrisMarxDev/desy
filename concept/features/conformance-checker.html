Rank 8 · Design-system evidence

Show exactly where the current artifact leaves the system.

After hot reload or before promotion, publish explainable registry, analyzer, runtime, scenario, and golden evidence into the current activity rail—without interrupting visual comparison or pretending automation can prove taste.

Impact 5/5Complexity 4/5Yield 1.25

Reason and user value

“Use the design system” is too soft for an agent and too expensive for a developer to verify repeatedly. Workshop diagnostics should name the violated rule, show the evidence, suggest registered alternatives, and become structured context for the next iteration.

Scope

  • Run a fast conformance pass after hot reload and a full receipt before promotion.
  • Validate registry IDs, component contracts, legal slots, knob domains, deprecated entries, and required theme context.
  • Add optional analyzer rules for high-confidence consumer policies such as raw colors, raw text styles, forbidden spacing literals, or bypassing an approved component.
  • Add runtime evidence from the real widget tree where static analysis is insufficient.
  • Show concise pass, warning, and error activity in the right rail; open exact source evidence in the center on demand.
  • Emit stable JSON/SARIF and include chosen findings in the next agent turn.
  • Let the consumer own enabled rules, severity, exceptions, and approved primitive escape hatches.

Non-goals

  • No claim that static or runtime checks can prove subjective visual quality.
  • No mandatory “Desy widgets only” policy.
  • No blocking of hot reload while advisory checks run.
  • No auto-fix when intent or semantics are ambiguous.
  • No inference of design-system truth from folder names or screenshots.
  • No Forui rule leakage into consumer previews.

Implementation sketch

  1. Define versioned DesyConformanceDiagnostic and DesyConformanceReport values with rule ID, severity, evidence, source target, candidate ID, and suggested registry references.
  2. Implement exact registry and contract checks first through the same read-only query service used by Agent Briefs.
  3. Expose desy check with stable machine-readable output.
  4. Add an opt-in analyzer plugin for a deliberately small set of high-confidence source rules.
  5. Have the Workshop run checks asynchronously after reload and show a compact status on each candidate.
  6. Feed selected diagnostics into the agent prompt and annotation loop; require a human decision for ambiguous fixes.

Acceptance criteria

  • A candidate using a forbidden raw color produces an exact, source-linked diagnostic and a registered token suggestion.
  • A candidate composing an attached component correctly does not receive a duplicate or unregistered-widget warning.
  • Checks never create a second registry or copied policy inventory.
  • Warnings do not prevent the widget from rendering or hot reloading.
  • Every suppression names the consumer-owned rule and its explicit rationale.
  • The next agent turn can consume diagnostics without scraping Workshop UI text.

Open questions

  • Which source rules are reliable enough to ship without noisy false positives?
  • How do consumers declare approved exceptions without creating boilerplate?
  • Can registry contracts express preferred composition strongly enough to suggest replacements?
  • Should accessibility rules live here or in scenario verification?
  • How are rules versioned with the registry and cached across rapid reloads?

Do or don’t?

Do in layers, after registry-aware Workshops exist. Impact 5/5, complexity 4/5, risk 3/5, yield 1.25. Exact registry and contract checks offer high trust. Source and runtime rules are valuable only when consumer-owned, narrow, and explainable. Refuse a single opaque “design-system score”; it would create false confidence rather than useful guidance.
