Rank 9 · Developer integration

Put the Desy feedback loop inside the app developers already run.

Extend the Registry Spine’s annotation protocol into an existing Flutter app: inspect the real screen, attach design requests, send structured context to the same developer-machine agent, and see repository changes through normal hot reload.

Run existing app→Inspect widget→Annotate→Agent edits Dart→Hot reload→Review in place

Reason and user value

Isolated component previews are fast, but many design problems only become obvious in the real route, state, navigation shell, data density, and responsive layout. Developers should be able to review that exact running context without recreating it in a separate workshop harness.

The value is continuity: feedback begins on the real widget in the real app and returns to that same state after the agent edits ordinary Dart.

Feasibility verdict

Feasible as a developer tool, with a required companion process. The in-app overlay and render-object selection are already proven. Structured annotations and a debug-service bridge are straightforward. Automatic hot reload is feasible only when a developer-machine process owns or attaches to the Flutter debug session; a running app package does not own its compiler or Flutter tool.

The beta may ship both halves from one package and one command. Their protocol must remain explicit so the runtime can later connect to a Desy CLI, IDE extension, or MCP server without rewriting the overlay.

Consumer integration

MaterialApp(
  builder: DesyDevOverlay.builder(
    registry: appDesignSystem,
    existingBuilder: existingBuilder,
  ),
)

The app-builder seam keeps the overlay below inherited app context and above the Navigator while preserving the routing child. A root wrapper remains available for a separate tool/desy_main.dart development entrypoint. Importing the package from production lib requires a normal dependency even when constant debug guards remove the runtime code; a true dev_dependency therefore uses the alternate entrypoint.

Developer workflow

dart run desy_dev_overlay:host \
  --target lib/main.dart \
  --device macos
  1. The host launches or attaches to the normal Flutter debug session.
  2. The overlay registers a debug-only service bridge and publishes review events.
  3. The host exposes those events to Codex, Claude, or another agent through a vendor-neutral adapter or MCP tools.
  4. The agent edits the consumer repository under its normal permission model.
  5. The host requests hot reload and returns compiler/runtime diagnostics to the overlay session.

Packaging decision

Keep setup simple but keep authority separated internally:

  • desy_overlay_protocol: pure Dart, immutable versioned session and annotation values.
  • desy_overlay: Flutter-only debug UI, inspector selection, and VM-service bridge; no file or process access.
  • desy_overlay_host: opt-in workstation CLI, agent adapters, repository access, Flutter runner attachment, and reload policy.

An umbrella setup command can add and configure these pieces. Package count is an implementation detail; the user-visible contract is one explicit development integration.

Scope

  • Debug-only root overlay with a small floating launcher and dismissible review panel.
  • App-wide render-object hit testing mapped to the nearest project-created widget.
  • Widget outline, source evidence when available, candidate ancestry, route, viewport, theme, and semantics summary.
  • Multiple direct design annotations grouped into one review turn.
  • Live references to the consumer’s existing DesyRegistry, including registered alternatives and source paths.
  • Vendor-neutral session protocol plus an initial Codex adapter.
  • Developer-hosted source editing, compile diagnostics, hot reload, and explicit restart fallback.
  • macOS dogfood first, then normal Android, iOS, web, Linux, and Windows debug targets through a desktop host.

Non-goals

  • No agent, shell, repository token, or source-writing capability inside a shipped app binary.
  • No production, profile, TestFlight, Play internal-testing, or customer-feedback SDK in the first version.
  • No replacement for Flutter DevTools, IDE debugging, or the normal Flutter toolchain.
  • No claim that every render object maps to a stable source-level widget after arbitrary edits.
  • No automatic design-system compliance score.
  • No copied component inventory; the active consumer registry remains authoritative.
  • No remote accounts, hosted agent execution, or multiplayer review in the local-first slice.

Implementation sketch

  1. Use Flutter’s public root WidgetInspector and WidgetInspectorService first for app-wide select mode and outlines. Keep the Workshop’s scoped custom hit tester only as a fallback where Desy must exclude its own chrome or inspect an isolated subtree.
  2. Create DesyDevOverlayConfiguration with the real registry, enabled capabilities, annotation sink, and explicit review-session policy.
  3. Wrap the consumer app in a debug-only root stack while keeping the review chrome’s theme and semantics independent from consumer UI.
  4. Define a versioned protocol for overlay state, widget targets, annotations, diagnostics, and reload receipts.
  5. Register the protocol as debug-only VM service extensions/events; never bind a public network server inside the app.
  6. Build a small host executable that launches or attaches to Flutter, runs the agent, exchanges protocol messages, and requests reload.
  7. Reuse Agent Brief and registry query services for context instead of serializing a second catalogue.
  8. Move agent-vendor commands behind adapters and keep the user’s repository permissions visible.

Smallest useful slice

  1. Integrate the package into a second, non-Desy Flutter app.
  2. Open the overlay and select any project widget on a real route.
  3. Add one annotation and copy a structured prompt containing widget type, source evidence, route, bounds, and comment.
  4. Let an externally running Codex session edit that widget.
  5. Use the host command to request hot reload.
  6. Keep the route and compatible widget state, then show whether the annotation target reattached.

Do not start by embedding a terminal, supporting every agent, or shipping a custom DevTools frontend. First prove that app-wide selection plus one annotated reload is better than the current manual loop.

Risks

  • Debug API maintenance: debugCreator, creation locations, and inspector internals may change across Flutter versions.
  • Target drift: widget identities are ephemeral; low-confidence annotations must detach rather than silently point elsewhere.
  • Input conflict: inspect mode temporarily intercepts app gestures and must be unmistakable and keyboard-accessible.
  • App fidelity: platform views, multiple windows, overlays, and nested navigators need explicit coverage.
  • Security expectations: the coding agent has ordinary repository permissions; the overlay is not a sandbox.
  • Integration weight: requiring the full Desy workbench UI in every app would be excessive; package dependencies and release tree shaking must be measured.

Open questions

  • Should the beta require an existing DesyRegistry, or permit generic annotations with reduced design-system context?
  • Is a root wrapper reliable enough, or should MaterialApp.builder be the primary integration?
  • Should the initial host own flutter run, or attach to IDE-launched sessions through the tooling daemon?
  • Can Flutter’s official MCP and tooling services supply reload and diagnostics so Desy avoids a private daemon protocol?
  • How should annotations behave across route changes and state restoration?
  • What is the measurable release-size impact when the debug wrapper is disabled?
  • Does this remain a Desy package, or become the default integration path once it works in two unrelated apps?

Acceptance criteria

  • Adding the overlay requires no copied component list and no alternate theme declaration.
  • With review mode disabled, all app interaction and rendering remain unchanged.
  • A selected project widget produces a visible outline and structured target record.
  • One annotation reaches an external agent and returns a compiler or reload receipt.
  • A successful edit hot reloads without losing the current route or compatible app state.
  • Release builds contain no active service bridge, agent process, file access, or review UI.
  • The package works in Desy dogfood and one unrelated consumer app before publication.

Do or don’t?

Do as a narrow package spike, not yet as a promised universal SDK. Impact 5/5, complexity 4/5, risk 3/5, yield 1.25. Desy already proves the difficult interaction primitives and same-process hot-reload workflow. The remaining uncertainty is reliable host attachment and a low-friction, release-safe consumer integration. Build the overlay plus one external-host reload in a second app; publish only if that integration stays small and the review loop is materially faster.

Primary-source feasibility evidence: Desy overlay package feasibility.

Decision: one developer install experience, two explicit runtime boundaries. Keep the app overlay read-only toward source; keep compilation, agents, and hot reload on the developer machine.
