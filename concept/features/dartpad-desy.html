Parked hosted-workshop research

Real Flutter files, compiled into shareable design workshops.

DartPad Desy is a possible hosted mode in which a consumer’s versioned design system becomes a Flutter compiler environment and workshop prototypes remain ordinary Dart files. Desy would compile, render, preserve, and share those files without introducing a Flutter-like DSL.

Design-system revision→Flutter files→DDC compiler→Isolated preview→Workshop journey

Reason and user value

Flutter developers can already iterate locally, but sharing an unfinished design journey requires code, a matching toolchain, and someone able to run it. A hosted compiler could make several real-widget directions reviewable from one link while preserving the source files that produced every round.

Potential win: actual Flutter authoring with browser-speed review, durable alternatives, asynchronous feedback, and a later path to agent or multiplayer collaboration.

Product boundary

The feature is not “run any Flutter repository.” It is a controlled UI workshop:

  • A versioned, web-compatible consumer design-system package supplies the real registry, widgets, themes, fonts, and assets.
  • Each workshop owns a small set of normal Dart prototype files.
  • A generated runner imports the selected prototype and applies the consumer’s real theme wrapper.
  • Platform logic, application backends, and production behavior remain outside the renderer.

Core product decision

DartPad Desy belongs only if Desy deliberately expands from a local design-system workbench into hosted collaborative Flutter authoring. It must remain an optional service derived from the consumer-owned registry and repository. It cannot become a second design-system source of truth or make hosted compilation necessary for ordinary Desy use.

Scope

  • Register a design-system revision as a cached compiler environment.
  • Store workshop prototypes as separate, ordinary .dart files.
  • Analyze and compile a typed file-map request with a known entrypoint.
  • Return compiler diagnostics and support DDC hot-reload deltas.
  • Render output in a credential-free, separate-origin iframe.
  • Preserve ordered rounds, candidates, comments, selections, source snapshots, and build hashes.
  • Publish read-only workshop links after an explicit save or snapshot action.

Non-goals

  • No Flutter subset, remote-widget format, or custom UI language.
  • No arbitrary whole-app execution or native platform plugins.
  • No unrestricted dependency installation during every edit.
  • No general-purpose cloud IDE, terminal, debugger, or production deployment.
  • No application business logic, secrets, authenticated APIs, or platform services.
  • No required agent, collaborative code editor, or multiplayer presence in the first slice.
  • No replacement for Desy’s local-first catalogue and preview workflow.

Smallest useful flow

Select design-system revision→Create three Flutter files→Compile and render→Comment and continue one→Save immutable round→Share read-only link

Implementation sketch

  1. Fork only the DartPad compiler/runtime pieces needed by Desy; do not adopt its editor UI.
  2. Extend the compiler request from one source string to a validated map of paths and source text plus one entrypoint.
  3. Create a cached environment keyed by Flutter SDK, design-system revision, lockfile, generated sources, fonts, and assets.
  4. Generate a small runner that imports a prototype builder and invokes the real consumer theme wrapper.
  5. Compile with DDC, return diagnostics and the delta kernel, and load the result in an isolated renderer frame.
  6. Store explicit source snapshots and compiled-build hashes as workshop rounds; treat live editor state as temporary.
  7. Add GitHub import/export only after the compiler and asset boundary is proven.

Technical evidence

  • DartPad’s backend already offers analyze and compile APIs and uses a persistent Dart Development Compiler worker.
  • Its current hot-reload path returns and accepts a delta kernel, so incremental Flutter web compilation is not speculative.
  • Upstream currently materializes only lib/main.dart; multi-file projects require a Desy-owned extension.
  • Packages are pinned and allow-listed in project templates. Consumer packages, generated files, fonts, and assets therefore need an environment-build stage.
  • The compiled preview remains untrusted browser code and requires origin, iframe, network, and resource isolation.

Value risk

Developers may prefer local hot reload and GitHub review once the novelty of browser compilation wears off. The workshop journey must prove value before the compiler service is justified.

Product risk

Hosted authoring can pull Desy toward accounts, storage, permissions, sync, IDE features, and general app building—well beyond its current design-system workbench focus.

Operational risk

Compiler isolation, package environments, assets, quotas, abuse prevention, versioning, caching, and long-term build reproducibility become product responsibilities.

Open questions

  • Is Desy primarily a local workbench, or should shared hosted workshops become a defining workflow?
  • Will teams value the recorded design journey more than a branch, PR, or ordinary preview deployment?
  • Must consumer design systems be separate publishable packages, or should monorepo path packages be supported?
  • How often may dependencies change before environment rebuilding interrupts the creative loop?
  • Can fonts, assets, code generation, and theme wrappers be reproduced reliably across revisions?
  • Should saved workshop source live in GitHub, Desy storage, or both—and which one is authoritative?
  • What access and retention model is acceptable for private design-system code?

Revisit triggers

  • The local Widget Workshop proves that developers repeatedly create, compare, and continue multiple real-code directions.
  • Users explicitly ask to share those journeys with people who cannot run the repository.
  • Desy chooses hosted collaboration as a product direction and accepts its account, security, storage, and operations costs.
  • A time-boxed spike compiles the dogfood design system with real fonts/assets and achieves an iteration loop worth using.

Do or don’t?

Don’t build now; preserve the option. Impact 4/5, complexity 5/5, risk 5/5, yield 0.80. The compiler mechanism is credible, but it commits Desy to a hosted product boundary before the workshop journey or collaboration demand has been validated. Revisit only after the local workflow proves repeat use and Desy consciously chooses hosted collaborative authoring.

Decision: parked concept. Keep real Flutter source and the consumer registry authoritative; do not let the compiler service choose Desy’s product direction by accident.
