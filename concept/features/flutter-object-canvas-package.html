Reusable package · finite object canvas

One small object canvas should power many editors.

Extract the interaction Desy is repeating in Sketch, collection canvases, and the screenshot builder into a neutral Flutter package: immutable typed objects, a controller, arbitrary widget builders, move, layout resize, transform scale, rotation, selection, finite bounds, and composable snapping—without importing any surrounding editor UI.

Typed object data→ObjectCanvasController→finite ObjectCanvas→host-owned tools and inspectors

Reason and user value

Many Flutter apps need a bounded poster, story, collage, annotation, document, or layout surface. They repeatedly rebuild the same selection frame, coordinate conversion, gesture arbitration, transform geometry, snapping, and guide painting before they can work on their actual domain.

Decision

Build a finite, content-agnostic object canvas—not an image editor or Desy canvas. The package owns geometry and interaction inside its bounds. The host owns object meaning, image loading, text models, toolbars, property screens, persistence, export, and application state.

Proposed authoring API

final controller = ObjectCanvasController<EditorElement>(
  canvasSize: const Size(1200, 630),
  defaults: const CanvasObjectDefaults(
    constraints: CanvasObjectConstraints(minSize: Size(24, 24)),
    capabilities: CanvasObjectCapabilities.all,
  ),
  objects: [
    CanvasObject(
      id: 'hero-image',
      data: ImageElement(bytes),
      geometry: const CanvasObjectGeometry(
        position: Offset(80, 64),
        size: Size(640, 360),
        rotation: 0,
        scale: 1,
      ),
    ),
  ],
);

ObjectCanvas<EditorElement>(
  controller: controller,
  objectBuilder: (context, object, state) =>
      buildElement(object.data, state),
  onAction: (event) => logCanvasEdit(event),
  snapping: CanvasSnapping(
    strategies: [
      CanvasEdgeSnapping(),
      ObjectAnchorSnapping(),
      GridSnapping(step: 8),
      AngleSnapping(stepDegrees: 15),
    ],
  ),
);

The controller is the single mutable owner. CanvasObject<T> stays immutable and typed. Canvas defaults provide the common minimum size and capabilities; individual objects override them only when exceptional. The object builder converts arbitrary host data into a real Flutter widget, while ObjectCanvas<Widget>.widgets provides a zero-builder default. Resizing changes geometry.size and therefore the widget's layout constraints; scaling changes geometry.scale and preserves its layout size. Each completed gesture becomes one typed CanvasAction backed by the undo package: pointer frames update only a visual draft, pointer-up adds one undoable change, and undo/redo restore the exact before/after object state.

Scope

  • A finite logical canvas with an explicit size, clipping, background, and boundary policy.
  • Immutable, ordered CanvasObject<T> values with stable IDs, typed host data, position, layout size, rotation, transform scale, pivot, constraints, and interaction capabilities.
  • A disposable ObjectCanvasController<T> for objects, selection, z-order, viewport, coordinate conversion, focused rebuilds, programmatic edits, and ephemeral undo/redo.
  • Typed move, resize, scale, rotate, add, remove, reorder, data, and composite actions; one completed interaction creates one history entry.
  • Mouse, touch, stylus, trackpad, and keyboard selection/move/resize/scale/rotate behavior using Flutter gesture and focus APIs.
  • Composable grid, canvas-edge, object-anchor, and angle snapping with targets precomputed on committed placement/configuration changes; pointer frames only query the index and render guides.
  • Builders/delegates for object content, selection frames, handles, guides, background, hit testing, modifier policy, and boundary resolution.
  • Adapters that prove the package in the screenshot builder first, then Sketch/Canvas V2, without moving Desy registry concepts into the package.

Non-goals

  • No sidebar, toolbar, details panel, layers panel, dialogs, routes, or application scaffold.
  • No built-in image picker, image codec, rich-text model, font catalogue, registry, or domain-specific object types.
  • No persistence format, JSON widget language, serialized history, collaboration, cloud state, or generated production code in V1.
  • No file export contract in the core; hosts may capture the content boundary or add a later focused companion.
  • No connectors, graph edges, drawing tools, shape catalogue, layout containers, groups, or infinite scene in the first package slice.
  • No custom replacement gesture arena unless a documented Flutter/dependency composition spike proves a required gap.

Architecture sketch

Host domain List<CanvasObject<T>>
  → ObjectCanvasController<T>
      committed document: canvas size + immutable paint-ordered objects
      view state: selection + viewport transform
      interaction state: one gesture draft + snap session + guides
  → ObjectCanvas<T>
      finite stage / clipping / background
      objectBuilder(T) → arbitrary host widget
      transform frame → move | layout resize | transform scale | rotate
      overlay builders → selection | handles | guides
  → CanvasAction<T> → undo.ChangeStack → apply | undo | redo

Pure geometry seam
  CanvasTransformEngine + CanvasSnapEngine + CanvasSceneIndex
  (no Desy registry, Forui, persistence, file IO, or editor chrome)

The implementation should extract and generalize the repository's proven snapping index/session and transient per-object geometry pattern. Flutter's InteractiveViewer/TransformationController remain the default camera primitives. Released transform dependencies may supply move/resize behavior; rotation is accepted only after a dependency/source and gesture-composition spike.

Rollout

  1. Freeze the public object, geometry, change-event, controller, and snapping contracts with API tests.
  2. Build a package example containing mixed image, text, and arbitrary-widget data on one finite canvas.
  3. Implement single selection, move, layout resize, transform scale, rotation, boundary containment, camera, and keyboard parity.
  4. Port the proven Desy snap engine, then add canvas-edge and angle strategies behind the same candidate/session contract.
  5. Adapt the screenshot builder. Delete its local geometry, selection, snapping, and resize code only after behavioral parity.
  6. Adapt Sketch/Canvas V2 next. Keep layouts, artboards, registry resolution, knobs, and inspectors in Desy.
  7. Consider richer multi-selection, persistent history, groups, or publishing only after two consumers prove the core boundary.

Open questions

  • Publish name: object_canvas, flutter_object_canvas, or a more distinctive name?
  • Ship only the canonical controller API in V1, or also a convenience objects + onObjectChanged constructor that internally owns and reconciles a controller?
  • Should transform scaling be an explicit active tool, a per-object capability, or a modifier on the standard resize handles?
  • Should onObjectChanged ship as a convenience projection over the primary CanvasActionEvent callback?
  • Should the default ephemeral history retain 100 completed document actions?
  • Does V1 need multi-selection transforms, or only a future-proof selected-ID set with single-object interaction?
  • Should viewport state live in the main controller or in a composable camera controller?
  • Can released dependencies cover rotation and rotated clamping, or must the first version own a narrow rotation handle/geometry seam?

Do or don’t?

Do, with extraction discipline. Impact 5/5, complexity 5/5, risk 4/5, yield 1.00. Desy already has multiple consumers and a benchmarked snapping core, so this is no longer speculative reuse. The risk is publishing an oversized editor framework or freezing a weak controller API. Keep V1 finite, typed, headless, controller-owned, and proven by two migrations before considering persistence or general scene-graph features.

Planned package boundary: geometry and interaction inside a finite canvas; every surrounding workflow remains host-owned.
