Value experiment

Let one day of messages become a useful, living nutrition view.

Calorie Day treats the conversation as a daily food log. Local Codex interprets each food message into one structured estimate, and a fixed GenUI surface keeps calories and macros visible without regenerating the surrounding interface.

Why it exists

Food tracking is naturally conversational: people remember meals in fragments, not as rows in a form. A persistent daily summary prevents the interaction from becoming a stream of unhelpful text confirmations.

User value

Users can log a meal in plain language and immediately see the cumulative day. The chart and meal list make the consequence visible while the chat remains the primary entry path.

Scope

Meal message→Local Codex interpretation→Day snapshot→A2UI data update

The app invokes the authenticated local Codex app-server with a constrained JSON schema for one meal entry. Flutter owns the resulting local day state, keeps one component graph alive, and updates that snapshot in one data-model operation.

Non-goals

  • No dietary, medical, or weight-loss recommendation.
  • No claim that free-form nutrition estimates are accurate.
  • No cloud food database, account, or health-data integration.
  • No model call for normal state refreshes.

Implementation sketch

  • Local Codex returns a schema-constrained typed entry and concise estimate notice for each food message.
  • A chat transcript and the daily log remain ordinary Flutter state.
  • A stable GenUI surface binds the daily aggregate to registered summary, chart, and meal-list components.
  • Only the Codex interpreter is provider-specific; another agent can replace it while preserving the handoff.

Acceptance evidence

"Oatmeal and berries" → Codex estimate → breakfast entry → calories and macro bars increase
"a chicken rice bowl for lunch" → Codex estimate → one updated daily snapshot

Every accepted entry must be inspectable in the day list. Ambiguous or non-food text must lead Codex to ask one clarification rather than add a fabricated entry.

Open questions

  • Should the entry schema include a confidence label or a confirmation step for uncertain portions?
  • Should targets be user-configurable, and how can that remain neutral rather than prescriptive?
  • Is an end-of-day generated recap more useful than the persistent chart?

Do or don't

Do the constrained tracking sample. It demonstrates a chat-first workflow with an obvious persistent visual payoff, a real local-provider call, and explicit data ownership. Do not add health advice or pretend model estimates are verified nutrition data.
