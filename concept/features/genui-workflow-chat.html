Concept reset · 2026-08-27

One chat runtime. Opinionated workflows. Real agent-generated turns.

Orbit should not ship a bespoke Product Decisions screen. It should prove a local-first GenUI workflow runtime where a named workflow such as /grilling drives one durable conversation and the agent renders each assistant turn as a real, interactive A2UI surface from a constrained catalog.

Decision

Build one generic workflow chat host in the GenUI exploration. Treat /grilling as its first workflow declaration and product-discovery proof. Do not continue the current Product Decisions screen or make its hand-authored Flutter cards the reference architecture.

Job to be done

A person starts with an open directional prompt, such as “Let’s create a better way to display step data” or “How could we visualize Flutter widgets live?” The workflow uncovers material unknowns, teaches concepts when needed, makes a concrete recommendation when sufficiently clear, and produces a copyable, implementation-agent-ready PRD handover.

Anti-goal

Do not turn this into generic prose chat, a fixed questionnaire, a static brief below chat, or a workflow-specific Flutter screen. A prose-only “next direction” is not useful progress. If uncertainty remains, ask through an interactive surface; if it does not, make the proposal.

Ownership and protocol boundary

Workflow declaration→Local agent→A2UI assistant-turn surface→Workflow runtime→Structured continuation
OwnerResponsibility
Workflow declarationStable ID, display metadata, agent instructions, allowed catalog subset, tools/client functions, turn rules, completion rule, and handover format.
AgentChooses whether the next turn should ask, explain, compare, or propose; composes only allowed real catalog components; never emits a prose-only non-turn.
Generic workflow runtimeOwns chat history, A2UI surface lifecycle, form/default state, event routing, local persistence, selected repository context, pending/error state, and copy/save behavior.
CatalogDefines legal semantic widgets and their data/event contracts. The agent does not invent widgets or callbacks.

Session model

  1. The user types a goal or starts a named workflow such as /grilling in the normal composer.
  2. The agent returns one assistant-turn A2UI surface. It contains either a useful interactive question batch, an explanation/comparison, or a direct proposal.
  3. An active question batch is one form. The user changes choices, writes custom context where needed, and moves through compact cards with previous/next arrows. The final next arrow submits the complete batch.
  4. The runtime submits one structured continuation containing all current values. Defaults count when untouched; user edits replace them.
  5. The submitted surface freezes into a compact history record. The next agent surface renders directly below it. V1 does not reopen earlier forms; corrections enter through the current composer and become new evidence.
  6. The session persists locally across app restarts. Completion yields a compact handover control with Copy, Save, and optional preview; raw Markdown is hidden by default.

Core workflow catalog

ComponentContract
workflow.questionnaireOne assistant-turn form with a title, concise context, ordered workflow.question children, local draft state, and one final continuation event. Arrow navigation never emits partial answers.
workflow.questionStable id, prompt, optional explanation, optional choices, defaults, allowMultipleAnswers, and always-available custom text. Empty choices make it a free-text-only question.
workflow.explainActionAvailable on each question. Emits the parent turn ID, question ID, current defaults, and edits. It never submits or resets the parent questionnaire.
workflow.clarificationSlotMount point directly below one question for an ephemeral child A2UI surface. That child may compose the allowed catalog, including definitions, comparisons, pros/cons, diagrams, and examples.
workflow.proposalA concrete decision, alternatives, trade-offs, and implementation direction. The agent uses it when material uncertainties are resolved rather than asking performative questions.
workflow.handoffClient-owned presentation for the full PRD payload: Copy, Save, and on-demand preview. It does not render a giant raw Markdown block in the transcript.

The runtime can continue to expose generic catalog elements—Markdown, tables, charts, diagrams, code, dates, files, and images—through each workflow’s allowed subset. The bespoke components above define the high-frequency AI decision interaction, not a parallel widget system.

Question payload

{
  "type": "workflow.continue",
  "turnId": "turn-7",
  "answers": {
    "rendering_strategy": {
      "optionIds": ["native-preview"],
      "customText": "Keep a browser export for sharing."
    }
  },
  "defaultedQuestionIds": ["scope"]
}

The payload preserves which choices were accepted untouched. The agent receives form state, not a guessed transcript.

Clarification rule

“Explain this” is an inline child turn, not an initial side chat. It leaves the parent form and answers intact, appears under the question that caused confusion, and is only promoted into the main handover when it materially changes the decision. A longer side conversation remains a later option, not a V1 dependency.

Guardrails

  • The workflow constrains the agent but does not script the next step. The agent decides whether enough context exists for a proposal.
  • Every choice-capable question has defaults. Every question permits custom text.
  • The final next arrow is the only submit action in a question batch. Widget edits are local until then.
  • Conversation order is chronological: user message first, then its generated assistant surface. Question cards are compact, bordered, and reveal the start of the next card where space permits.
  • Each assistant message is a real A2UI surface backed by the declared catalog—not a Flutter renderer that happens to resemble generated UI.
  • Repository root is local workflow context for Codex tools. It is persisted locally and never becomes prompt text by accident.
  • V1 uses subset catalogs. The full catalog can become available to more capable agents later without changing the chat runtime contract.

Implementation sequence

  1. Remove the Product Decisions-specific renderer from the reference path and introduce the generic workflow/session abstractions.
  2. Define and register the workflow catalog above; validate A2UI output and interaction payloads.
  3. Teach the local Codex GenUI bridge about per-turn surfaces and the persisted repository working directory.
  4. Implement /grilling as the first declaration, including inline clarification child turns.
  5. Add local session persistence and PRD handover export after the live turn loop is reliable.
