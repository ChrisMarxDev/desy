Provider controls

Choose the active agent and model in one place; manage local runtimes separately.

Orbit needs one reactive source for the selected provider, model, and runtime status. A compact control keeps the active configuration visible, while a dedicated settings route handles installation and diagnostics without turning setup into a chat-side chore.

Decision

Use GoRouter for the app’s destinations. Keep the active provider and model in the state-beacon-backed AI controller. Provider bridges remain provider-specific and are only responsible for probing, installation, authentication, and generation.

Interaction

The sidebar footer shows one provider-and-model control. It opens upward: first choose a provider, then choose one of that provider’s models. A Manage providers action opens the settings route.

Settings route

  • Show OpenAI server, Codex local, and Claude local as runtime rows.
  • Each row exposes a clear status: Ready, Installed, Needs sign-in, Needs install, or Unsupported.
  • Check again refreshes local command and login probes.
  • Install launches the existing visible Terminal flow; no credential is read by Flutter.
  • Provider/model configuration is selected through the shared controller, never through launch-time flags.

Boundary

Impact 4/5 · Complexity 3/5. This is app-shell and experimental Orbit work, not a Desy package contract. The controller is deliberately typed around provider selection, model selection, backend routing, and status—not a generic map of arbitrary provider settings.

Internal concept artifact. Offline-safe; no remote assets or runtime dependencies.
