One command turns the real registry into deterministic golden evidence.

A thin local command launches Flutter’s headless widget-test runner. Inside that runner, Desy derives a complete default matrix from every registered component, real theme, named instance, and scenario; Flutter performs the rasterization and comparison.

Desy registry→Complete derived plan→flutter test→PNGs + JSON receipt

Reason and user value

Golden tests catch visual regressions, but hand-authored harnesses duplicate theme, sizing, component, and naming knowledge. Desy already owns those addresses and builders. The proposed tool removes repetitive wiring while leaving test intent, baseline acceptance, and platform policy under the consumer’s control.

Decision

Use flutter test as the rendering engine. A plain Dart process cannot mount a consumer registry whose declarations import Flutter and dart:ui. A hidden desktop executable adds window-manager and GPU variability. Flutter’s widget-test binding is the smallest supported headless boundary and already owns golden comparison and --update-goldens.

MVP commands

  • dart run desy_goldens plan expands and prints the selected matrix without comparing pixels.
  • dart run desy_goldens verify launches the headless Flutter test and never mutates baselines.
  • dart run desy_goldens update --accept launches the same test with Flutter’s explicit golden-update mode.

Do not add separate capture and diff commands in V1: explicit update creates missing baselines, and Flutter’s local comparator already writes mismatch images.

Consumer entrypoint

// test/desy_goldens_test.dart
void main() => desyGoldenTests(
  registry: appDesignSystem,
);
// Optional additions and exceptions only.
void main() => desyGoldenTests(
  registry: appDesignSystem,
  options: DesyGoldenOptions(
    additionalFrames: [DesyGoldenFrame.phone],
    additionalCases: [checkoutLoadingCase],
    exclusions: [
      DesyGoldenExclusion(
        componentId: 'app.component.live-map',
        reason: 'Native map surface has a separate integration test.',
      ),
    ],
  ),
);

The first form is the normal setup. Options are additive or explicit exceptions; they never restate the registry inventory.

What becomes a case

  • Every registered component’s default preview.
  • Every named instance and every declared scenario for that component.
  • Every declared real consumer theme.
  • One canonical content frame, device-pixel ratio, locale, text scale, and accessibility environment by default.
  • Additional frames or bespoke knob-value cases only when the consumer asks for them.
  • One deterministic filename derived from component, variant, theme, frame, and environment IDs.

Determinism contract

  • Pin Flutter SDK, operating-system image, and bundled font files in CI.
  • Load fonts before tests; never depend on host-installed fonts.
  • Use an explicit locale, logical size, pixel ratio, and text scale for every case.
  • Default to a fixed pump policy. Infinite animations must use a named frame checkpoint instead of universal pumpAndSettle.
  • Block network images and uncontrolled clocks in the deterministic suite.

Deterministic registry-to-golden wiring

  1. Derive. DesyGoldenPlan.fromRegistry(registry) reads the immutable registry directly and includes every component default, named instance, declared scenario, and theme. No suite inventory is authored beside it.
  2. Augment. Optional values may add frames or bespoke knob-value cases, or exclude an inherently non-deterministic target with a required reason. Overrides never replace the derived inventory wholesale.
  3. Validate. Plan compilation rejects registry errors, duplicate case IDs, unresolved addition/exclusion IDs, invalid frame geometry, and exclusions without reasons before any widget is mounted.
  4. Order. Derived cases are sorted lexicographically by stable IDs. The compiler emits canonical JSON and a SHA-256 plan digest so declaration order cannot change baseline identity.
  5. Resolve. At render time, a case resolves directly against the supplied registry: default uses component.preview, an instance uses component.buildInstance with registry.widgetBuilder, and a scenario uses its declared builder. Nothing is copied into another catalogue.
  6. Host. The harness supplies the same minimal Flutter preview shell used by Desy and automatically loads bundled font assets. A runtime-only bootstrap is available only for consumer localization, dependency scopes, clocks, or image fakes that the registry cannot derive. The selected registry DesyTheme.wrap remains authoritative.
  7. Frame. The harness resets WidgetTester.view, sets explicit physical size and device-pixel ratio, installs fixed locale/text/accessibility values, and renders without Desy canvas zoom or fit transforms.
  8. Settle. The case advances fake time using a typed fixed policy. Continuous animations require an explicit named checkpoint; a universal pumpAndSettle is forbidden.
  9. Compare. Flutter’s configured comparator owns verification and update. Desy supplies only the stable golden key and records the outcome.
  10. Receipt. The harness writes the plan digest, case ID, component source path, resolved IDs, bootstrap ID/version, logical and physical geometry, font hashes, Flutter/engine/platform fingerprint, baseline path, and diff path.

Stable case identity

app.component.badge/
  instance.outline/
  app.theme.dark/
  frame.content/
  environment.standard.png

Only stable IDs participate in the key; display names, source ordering, and paths do not. A default preview, named instance, and scenario are distinct variant kinds. No suite ID or unrelated DesyCatalogConfig is required, so a minimal registry becomes golden-testable immediately.

Execution flow

  1. The command resolves test/desy_goldens_test.dart or an explicitly supplied entrypoint.
  2. It invokes flutter test with a Desy mode and report path under .dart_tool/desy/goldens/; update mode additionally passes Flutter’s update-goldens flag only after --accept.
  3. The test imports the consumer’s registry declaration directly, runs normal registry validation, and derives an immutable canonical case list from every component, instance, scenario, and theme.
  4. For each case, the harness resets and configures the Flutter test view and media values, enters the consumer bootstrap, wraps the widget with the selected DesyTheme, then resolves the real default, named instance, or scenario builder.
  5. The harness pumps according to the declared settle policy and delegates comparison or update to Flutter’s golden comparator.
  6. It writes a JSON receipt containing case IDs, source paths, environment fingerprint, outcomes, baseline paths, and diff paths. The command forwards Flutter’s exit code.

Package boundary

Prototype this as an optional packages/extensions/desy_goldens package. Keep the immutable derived-plan model separate from its flutter_test harness, and keep the executable as a small orchestrator. The consumer imports this package only from a test entrypoint. Do not place test-runner concerns in desy_bench core, depend on the app entrypoint, or reuse the interactive Screenshot Builder scene model.

Baselines and receipts

Commit baseline PNGs beside the consumer test suite. A newly registered component, instance, scenario, or theme automatically creates a planned case; normal verification reports its baseline as missing and never accepts it silently. Keep ephemeral diffs and the latest JSON receipt out of source control. The receipt identifies the registry/catalog version, Flutter version, platform, locale, font fingerprint, derived case, and exact stable IDs so CI and the Registry Spine can explain a failure without parsing console prose.

Non-goals

  • No silent baseline updates or agent-side acceptance.
  • No hosted comparison service in the first release.
  • No claim that one baseline is stable across arbitrary Flutter versions or operating systems.
  • No automatic capture of all knob combinations, generated GenUI surfaces, or Screenshot Builder scenes.
  • No source generation beyond optional ephemeral runner data under .dart_tool.

Open questions

  • Should the executable be published as desy or the narrower desy_goldens while the broader CLI is deferred?
  • Should content-sized frames join the fixed-viewport MVP, and what finite loose constraint should define their intended logical size?
  • Which typed atom lanes should become automatic golden cases after component coverage is proven? Motion and media need lane-specific settle and capture policies.
  • Should the harness use Flutter’s exact comparator only, or allow an explicit consumer-supplied comparator later?
  • Which Registry Spine activity surface should consume the JSON receipt after the CLI is proven independently?

Rollout and acceptance

  1. Spike: one dogfood component, two themes, one fixed viewport, one committed baseline, and verified non-zero exit on mismatch.
  2. MVP: automatic component/default/instance/scenario/theme expansion, canonical plan digest, deterministic naming, plan/verify/update commands, automatic bundled-font loading, optional consumer bootstrap, and JSON receipt.
  3. Product integration: show the latest focused receipt in Registry Spine only after CLI behavior is stable.

Acceptance requires identical reruns on the pinned CI image, a useful Flutter-generated diff after a deliberate one-pixel change, no mutation during verify, explicit acceptance for update, and proof that every rendered target came from the supplied registry.

Do or don’t?

Do the selected-matrix MVP. Impact 5/5, complexity 3/5, risk 2/5. The repository already has stable registry identities, real theme wrappers, default previews, named instances, scenarios, and PNG capture precedent. The main risk is environmental pixel drift, which is bounded by pinning one CI renderer rather than building a custom rendering runtime.

Decision: a thin CLI orchestrates Flutter’s headless test runner; the consumer registry remains the only widget inventory and Flutter remains the rasterizer and comparator.
