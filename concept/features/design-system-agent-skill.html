Keep the Registry Spine workflow independent of one coding agent.

Ship an installable repository skill backed by stable CLI queries. The right rail may host Codex or Claude Code, but the skill defines the same registry-first, annotate, hot-reload, verify, and promote behavior for either.

Reason and user value

Repository instructions can tell an agent to respect a design system, but cannot reliably enumerate its live components, contracts, or valid states. A Desy skill makes the method durable while commands keep the facts current.

Scope

  • desy registry inspect, search, validate, and export.
  • desy brief and golden verify as agent workflow steps.
  • Stable JSON output with schema/version metadata.
  • A compact SKILL.md that requires registry lookup before authoring UI.
  • Optional installation into common repository agent-instruction locations.

Non-goals

  • No agent-specific business logic inside desy_bench.
  • No generated prose dump of every component.
  • No direct source modification by the CLI.
  • No assumption that one agent vendor owns the workflow.

Implementation sketch

  1. Stabilize a read-only CLI query protocol over the registry export.
  2. Define agent-safe commands with bounded output and exact source paths.
  3. Create a reusable skill template referencing those commands.
  4. Add a consistency check: exported registry hash and skill version.
  5. Dogfood the skill on Desy itself and a second consumer repository.

Agent contract

Before implementing Flutter UI:
1. Run `desy registry search --intent ... --json`.
2. Inspect exact components, instances, contracts, and source paths.
3. Use consumer-owned widgets; do not recreate them.
4. Run `desy validate` and the focused golden plan.
5. Report any missing registry capability instead of inventing one.

Open questions

  • Can registry construction run cheaply enough for frequent CLI queries?
  • Should a derived cache be permitted, and how is staleness detected?
  • Which agent skill formats deserve first-class installers?
  • How should intent search work before semantic metadata exists?

Do or don’t?

Do after the first CLI query surface exists. Impact 5/5, complexity 2/5, risk 2/5, yield 2.50. This is largely a protocol and guidance boundary rather than a new visual workflow. The key refusal is duplicating component facts into a generated skill; commands must remain authoritative.

Decision: skill owns agent behavior; CLI owns current facts; registry owns truth.
