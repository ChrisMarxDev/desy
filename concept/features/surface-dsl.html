A small DSL for composing real design-system widgets.

Developers and agents describe a screen using registered component-instance IDs, serializable values, and trusted structural nodes. Desy validates the payload and renders the consumer’s real Flutter widgets immediately.

Reason and user value

Screen ideas can be evaluated before app architecture is committed. The DSL gives agents a constrained prototyping language and gives developers a fast visual result without permitting invented widgets or arbitrary Dart execution.

Scope

  • Versioned DesySurfaceManifest as the canonical typed model.
  • JSON authoring shorthand plus an optional typed Dart builder.
  • Structural nodes: column, row, stack, scroll, padding, align, spacer.
  • Leaf nodes reference registered component instances.
  • Values validated against the owning component’s knob schema.
  • Read-only preview, diagnostics, and import/export with Sketch.

Proposed DSL

{
  "version": 1,
  "surfaceId": "testing-screen",
  "root": {
    "layout": "column",
    "children": [
      {
        "nodeId": "header",
        "component": "title.headerbar.default",
        "values": {"title": "Testing Screen"}
      },
      {
        "nodeId": "chart",
        "component": "charts.barchart.default",
        "values": {"x": [1, 2, 3], "y": [4, 6, 7]}
      }
    ]
  }
}

The JSON is only an input format. Parsing produces sealed typed nodes and typed knob values before rendering. Supporting chart data requires explicit serializable list/data knob contracts; it must not become an untyped escape hatch.

Non-goals

  • No callbacks, Dart expressions, imports, or arbitrary widget construction.
  • No business logic, navigation, networking, or persistent app state in the first slice.
  • No production Dart generation.
  • No independent DSL component catalog.

Implementation sketch

  1. Define sealed surface/layout/component/value nodes with schema versioning.
  2. Add a validator that resolves every component ID and knob value through DesyRegistry.
  3. Build a renderer that receives the same registry/theme context as Sketch.
  4. Expose parse diagnostics with JSON paths and registry suggestions.
  5. Add a source editor + preview workspace extension.
  6. Only then add Sketch round-tripping and agent generation.

Open questions

  • Are layout primitives built into the manifest or registered like components?
  • How should responsive alternatives be represented without flags everywhere?
  • Do values support literal data only, or read-only bindings to named sample data?
  • How are component slots represented versus ordinary layout children?
  • Should JSON be the only text syntax, or should YAML be accepted for humans?

Do or don’t?

Do a read-only prototype. Impact 5/5, complexity 4/5, risk 3/5. The feature is central to agent prototyping, A2UI, and SDUI, but actions and state would expand it into an application platform too early.

Decision: one manifest shared with Sketch and adapters; DSL syntax is not a second registry.
