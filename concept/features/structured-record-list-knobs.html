Registry / GenUI boundary

Portable collections without making the registry object-shaped.

Charts, diagrams, and structured agent output need ordered values and occasional metadata. The registry should declare those inputs once, Bench should edit them locally, and the GenUI adapter should derive their JSON schema from the same declaration.

Problem

Existing Desy knobs cover scalar values, events, and registered widget composition. A chart needs labels and numbers, but a Dart record-list would make the handoff language-specific. Conversely, encoding everything as a JSON string gives up validation, usable controls, and catalogue schema generation.

Committed bounded contract

Add three opt-in JSON-shaped inputs: stringList, numberList, and jsonValue. The first two are immutable, typed lists with precise catalogue schemas. jsonValue carries a decoded JSON root for semantic metadata when a consumer genuinely needs it; it is not a JSON string and it is never interpreted as widgets, callbacks, or Dart objects.

One declaration, three consumers

  1. The consumer component reads the typed record list to render its real Flutter widget.
  2. Bench edits lists as comma-separated values and JSON as validated decoded JSON, preserving changes only as ephemeral preview state.
  3. desy_genui derives A2UI JSON schemas and validates agent-supplied data before the widget builds.

First proof

Orbit exposes bar and pie chart components. Both take parallel labels and non-negative values lists; their consumer builder zips those into its private chart view model. Markdown continues to use an existing string knob. A future diagram can declare separate lists or a jsonValue payload; it does not require a chart-specific Desy feature.

Non-goals

This does not create a JSON widget editor, persist component state, add generated Dart code, introduce a record-list DSL, or make arbitrary app APIs writable from a chart. It is a small typed declaration and preview-editing capability.
