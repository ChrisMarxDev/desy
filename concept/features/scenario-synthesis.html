Constraint-aware coverage

Generate the states that actually break UI.

Use component contracts and typed knobs to propose a small, meaningful matrix across content, state, viewport, theme, locale, and text scale.

Impact 4/5Complexity 4/5Risk 3/5

Reason and user value

Agents often test the happy path they just built. Desy can systematically ask for long labels, empty data, errors, disabled actions, large text, dark theme, and narrow widths—without rendering every possible combination.

Scope

  • Constraints and interesting-value hints on typed knobs.
  • Pairwise or risk-based scenario planning.
  • Named accessibility presets for text scale, contrast/theme, focus, and reduced motion.
  • CLI output that can feed golden and widget tests.
  • Coverage report showing declared, generated, skipped, and redundant states.

Non-goals

  • No exhaustive Cartesian product.
  • No fabricated business data in core.
  • No replacement for hand-authored semantic scenarios.
  • No automatic baseline acceptance.

Implementation sketch

  1. Introduce optional knob-domain constraints and interesting values.
  2. Generate a deterministic plan with a documented selection algorithm.
  3. Let consumers approve or persist chosen scenarios in the registry.
  4. Run approved states through golden, semantics, overflow, and exception checks.
  5. Teach the agent skill to add missing high-risk scenarios.

Open questions

  • Should generated scenarios remain ephemeral or graduate into declarations?
  • How is risk weighted across component types?
  • Can Flutter semantics assertions be normalized across platforms?
  • How should sample data privacy be handled?

Do or don’t?

Do after golden recipes are deterministic. The feature’s value comes from selecting better inputs; it should reuse the test runner rather than invent another one.

Offline concept artifact. No remote assets or runtime dependencies.
