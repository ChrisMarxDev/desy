Rank 12 · Runtime platform

Server-driven UI constrained by the app’s Desy registry.

A later runtime lets a server select and compose only the widgets, values, and events pre-approved by the shipped Flutter app. The payload is data; implementation and trust remain client-owned.

Reason and user value

Teams could change forms, onboarding, dashboards, experiments, and operational flows without shipping new widget code for every arrangement. Unlike generic SDUI, Desy can guarantee that every visual element resolves through the application’s real design system.

Scope

  • Transport versioned DesySurfaceManifest payloads.
  • Negotiate registry/catalog fingerprint and supported capabilities.
  • Resolve only shipped component-instance IDs and legal values.
  • Allow host-registered named events with typed serializable payloads.
  • Verify signatures/integrity where the threat model requires it.
  • Cache last-known-good surfaces with expiry and bundled fallback.
  • Expose diagnostics, telemetry hooks, and kill switches to the host app.

Non-goals

  • No remote Dart, scripts, callbacks, arbitrary URLs, or widget code.
  • No remote expansion of the client’s permissions or capabilities.
  • No business-logic language.
  • No replacement for ordinary Flutter navigation and application architecture.
  • No requirement that Desy Bench itself host the server.

Implementation sketch

  1. Stabilize manifests locally through the DSL and Sketch first.
  2. Define capability document: registry hash, schema versions, components, values, events.
  3. Implement parser, validation budget, depth/size limits, and safe error widgets.
  4. Add transport-neutral fetch/update interfaces owned by the consumer.
  5. Add cache/fallback and staged rollout controls.
  6. Prove one bounded workflow such as a read-only dashboard before forms/actions.

Open questions

  • Is the first use case generative UI, product-controlled SDUI, or both?
  • What event vocabulary remains useful without becoming business logic?
  • How are offline and stale manifests communicated to users?
  • Can old app versions safely render new server surfaces?
  • Which data-binding operations are expressive yet auditable?

Do or don’t?

Research now; build later. Impact 5/5, complexity 5/5, risk 5/5. The registry makes SDUI safer, but transport, security, compatibility, state, and operations are a separate product tier. Do not let this delay local developer tooling.

Decision: same manifest renderer, separate hardened runtime package, consumer-owned transport.
