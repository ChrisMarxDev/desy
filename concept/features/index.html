Feature index

See the real system. Workshop what it becomes.

Desy is a local-first Flutter design workspace. The registry is the persistent map, real Dart is the editable material, hot reload is the feedback engine, and the agent is a replaceable collaborator inside one continuous design journey.

Registry sidebar→Construct→Real Dart + hot reload→Review→Promote

The product is the Registry Spine workspace

Use one stable desktop shell: a live registry spine on the left, a mode-aware construction canvas in the center, a conversation and activity rail on the right, and one global annotation layer. A compact Sessions frame sits at the bottom of the registry spine. The consumer registry remains the only inventory and accepted work becomes ordinary consumer-owned Flutter source.

Visual commitment

White structural surfaces, 1px neutral dividers, compact Roboto typography, small radii, black primary actions, and pink reserved for selection and annotation. The language is shadcn-like desktop tooling translated through a Desy-owned Forui theme rather than a web CSS dependency.

Hard boundary

No JSON widget editor, Flutter subset, parallel component catalogue, or general-purpose IDE in the core product. Desy may preserve research into hosted or protocol adapters, but none may bend the local real-Dart workflow.

Ranked by practical yield

Complexity includes implementation, interaction design, visual states, accessibility, and the validation needed to make a workflow trustworthy. Higher value per unit of complexity comes first; ties favor broader practical value and lower dependency risk. This is an effort map, not the dependency-aware build sequence below.

Recommended sequence

  1. Build the committed Registry Spine shell around the existing Atlas and Workshop primitives.
  2. Lift widget inspection and annotation into the shell.
  3. Make sessions resumable in the compact bottom-left frame and conversation rail.
  4. Finish the wide-to-deep candidate loop and delete rejected implementations after selection.
  5. Add explicit promotion into real design-system source.
  6. Attach conformance and golden receipts to the hot-reload activity stream.
  7. Only then test the overlay in an unrelated consumer app.

Shared enabling work

  • A Flutter-native registry kernel that does not depend on workbench UI.
  • One app-wide workspace focus object containing stable registry IDs and preview state.
  • One source-aware widget-target and annotation value.
  • One replaceable resumable agent-runtime interface.
  • Ordinary Dart candidate files and a resident hot-reload boundary.
  • One explicit prototype-to-production promotion transaction.
  • Deterministic machine-readable verification receipts.

Parked research, not planned product work

Surface DSL, SDUI, and hosted DartPad Desy remain readable research records. They are intentionally outside the ranked plan because the chosen product works on real local Flutter code rather than a serialized UI language or hosted compiler. The ranked registry capability architecture preserves a clean route for optional runtimes without committing Desy to an SDUI platform; the GenUI catalog remains the first bounded interoperability proof.

Planning hygiene

This index is the single home for planned product work. Every ranked row links to one complete concept artifact; implemented contracts move to docs/concepts/, research evidence remains in docs/research/, and agent instructions link here rather than carrying their own feature lists.
