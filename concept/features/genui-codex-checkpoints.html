Value experiment

Ask for a decision only when it changes the code.

Codex Checkpoints is a task-oriented GenUI experiment. A coding agent pauses at a material fork, presents structured evidence and approved choices, then receives the user’s choice as a canonical continuation action.

Why it exists

Chat forces consequential architecture choices, patch approval, and verification status into prose. That makes choices hard to compare and easy to lose in a long task transcript.

User value

Developers inspect a bounded decision with affected files and evidence, choose deliberately, and see the same task continue. The interface exists only for the checkpoint; normal coding progress remains ordinary task output.

Scope

Start coding task→API scope checkpoint→Verification checkpoint→Patch acceptance

The first slice is a deterministic local task driver using the same GenUiPromptTurn, GenUiActionTurn, and generated-surface interface as a provider adapter. It demonstrates the handoff before a live Codex turn owns actual repository changes.

Non-goals

  • No autonomous shell command, patch application, or git write.
  • No generated dashboard or permanent project-management view.
  • No claim that every status update needs AI or GenUI.
  • No substitution of the existing local Codex driver in this slice.

Implementation sketch

  • A task driver owns the checkpoint state machine and validates legal choices.
  • The workbench creates one A2UI surface and passes generated actions back as typed turns.
  • Orbit renders only registered cards, evidence, tasks, and explicit approvals.
  • Later, the local Codex adapter can take the driver’s place without changing the workbench action seam.

Acceptance evidence

Start task → choose public or experimental API → inspect proposed patch → run verification → accept or request revision

Each transition must be driven by a generated UI action, preserve the task’s current surface as continuation context, and clearly state that fixture transitions never execute a repository command.

Open questions

  • Which real Codex task events should request a checkpoint rather than continue autonomously?
  • How should a live driver include bounded diff and test evidence without exposing arbitrary filesystem authority?
  • Should the user be able to reopen a completed checkpoint as task history?

Do or don't

Do the narrow checkpoint experiment. It directly tests the value that static reports lacked: a user decision changes an ongoing task. Keep it local and non-writing until that continuation loop feels more useful than prose.
