Know what an accepted design-system change can break.

Before promotion, connect typed foundations, component instances, registered compositions, scenarios, and golden recipes into an explainable review graph.

Impact 4/5Complexity 4/5Risk 3/5

Reason and user value

A design-system change becomes safer when developers and agents can ask “what should I inspect and retest?” and receive evidence instead of a full-suite guess.

Scope

  • Exact edges for manifest component references, registry instance dependencies, scenarios, and golden recipes.
  • Optional source-derived edges marked with confidence and origin.
  • Registry snapshots and semantic diffs: added, removed, deprecated, contract-changed, visual-input-changed.
  • desy impact output for affected previews, tests, and migration hints.
  • Machine-readable reports for agents and CI.

Non-goals

  • No promise of perfect Dart call-graph analysis.
  • No hidden telemetry or hosted dependency service.
  • No automatic semantic-version decision without consumer policy.
  • No silent registry migration.

Implementation sketch

  1. Define a stable registry snapshot and semantic diff format.
  2. Record exact edges while validating manifests and golden recipes.
  3. Add optional analyzer-produced evidence with confidence labels.
  4. Calculate affected sets and explain every traversal path.
  5. Integrate with golden planning and deprecation guidance.

Open questions

  • Can token usage be declared explicitly without too much boilerplate?
  • What snapshot data is safe and stable across Flutter versions?
  • How should aliases and renamed IDs preserve history?
  • Which changes should block CI versus request review?

Do or don’t?

Do once surfaces and golden recipes create exact edges. Start honest and partial; an explainable incomplete graph is more useful than opaque “affected” magic.
