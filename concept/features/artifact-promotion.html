Turn the chosen direction into the real design system.

Promotion is the explicit transaction between temporary Workshop Dart and consumer-owned production source. It shows what will move, which registry declarations will change, what evidence exists, and the exact reviewable diff before anything becomes part of the system.

Reason and user value

Hot reload makes exploration fast, but without a clear end state prototypes either accumulate forever or leak into production through ad-hoc copy and paste. Promotion makes the moment of commitment visible and keeps the registry, source, scenarios, and tests synchronized.

Scope

  • Promote exactly one selected candidate or constituent part.
  • Choose or confirm the destination source file and component path.
  • Reuse existing registry IDs or create deliberate new stable IDs.
  • Show source moves, imports, registry declarations, scenarios, and focused tests as one proposed diff.
  • Run analyzer and focused verification before acceptance.
  • Remove temporary candidate files only after the production diff succeeds.

Non-goals

  • No automatic acceptance because a candidate hot reloaded.
  • No hidden source movement or registry mutation.
  • No production Dart generation from a DSL or canvas model.
  • No requirement to promote an exploratory session.
  • No bulk migration system in the first slice.

Implementation sketch

  1. Create a typed promotion plan containing the prototype source, destination, registry identity, and required declaration changes.
  2. Ask the agent runtime to prepare—not commit—the production diff.
  3. Resolve registered dependencies by stable ID and reject copied substitutes.
  4. Run focused analyzer, widget, and optional golden checks.
  5. Present the diff and receipts in the center workspace.
  6. On acceptance, keep Git as the durable record and update the active Registry Spine focus to the production artifact.

Workspace flow

Select one direction→Refine its parts→Promote→Review diff + receipts→Accept→Reopen from registry

Open questions

  • Which destination facts may Desy derive safely from the registry and source evidence?
  • Should an existing component promotion preserve the original ID automatically?
  • How are partial promotions handled when a candidate contains several new reusable parts?
  • Who owns cleanup if verification fails after files moved?

Do or don’t?

Do immediately after the unified workspace shell. Impact 5/5, complexity 4/5, risk 2/5, yield 1.25. Without promotion the Workshop is a compelling demo but not a complete daily workflow. The reviewable transaction and diff experience add meaningful interaction design, so keep the first version explicit, local, reversible through Git, and limited to one artifact.

Decision: exploration stays temporary until a human accepts one explicit production diff.
