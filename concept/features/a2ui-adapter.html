Rank 10 · Optional interoperability

Declare the design system once. Generate the agent catalog from it.

Let a Desy consumer opt into a narrow GenUI/A2UI catalog generated from the same registry, typed knobs, named instances, and real widget builders already used by the workbench. Desy supplies component capability; the consuming app and backend continue to own agents, authentication, actions, and business logic.

Impact 4/5 Complexity 3/5 Risk 3/5 Yield 1.33

Reason and user value

A Flutter team that already describes its real components in DesyRegistry should not maintain a second hand-authored catalog for a generative UI agent. A derived catalog makes the design system consumable by the Flutter renderer and a separate agent backend while preserving Desy’s single-registry ownership.

The immediate value is interoperability: teams can test Dartantic, ADK, Flue, Go, or another backend against one stable component vocabulary without placing model keys or provider logic in the Flutter app.

Product boundary

This is an optional compiler capability, not a new Desy runtime or hosted service. The registry remains ordinary consumer-owned Dart. GenUI remains responsible for A2UI surfaces and data. The consuming application remains responsible for transport and event dispatch. The backend remains responsible for models, tools, policy, authorization, and business operations.

Concept in one line

DesyRegistry→ Optional CatalogConfig→ Derived schemas + real builders→ Flutter GenUI Catalog+ Backend catalog.json

Smallest useful scope

1. Catalog identity

Add an optional registry-level DesyCatalogConfig containing a stable catalog ID, version, and optional description. Without it, Desy behaves exactly as it does today and exposes no catalog-generation surface.

2. Derived components

Include every representable registered component by default. Add optional component-level DesyComponentCatalogConfig only for exclusion, model-facing guidance, or future event overrides. Do not require repeated opt-in boilerplate.

3. Existing knobs

Generate scalar schemas from string, number, and boolean knobs. Generate component references from instance-swap knobs. Add an optional knob description and show it in both Desy’s component controls and exported catalog.

4. Multiple children

Add one plural widgetInstances knob. It resolves a list of real widgets in Desy and maps to an explicit A2UI child list in the generated catalog. It is not a new slot system.

5. Events

Add an event knob whose value is an emitter used by the real widget builder. emit() covers the common no-payload case; emit({...}) may forward an optional JSON object without declaring its schema in Desy. Desy preview supplies a harmless host and the GenUI adapter supplies an A2UI action dispatcher.

6. Generated examples

Emit one catalog item per component. Do not add an examples API or export named instances as separate catalog items. Named instances already contain serializable knob values and become optional model examples and conformance fixtures. Callback-only visual scenarios remain workbench-only.

Registry-level config

final class DesyCatalogConfig {
  const DesyCatalogConfig({
    required this.id,
    required this.version,
    this.description,
  });

  final String id;
  final String version;
  final String? description;
}

The protocol adapter may add a pinned A2UI version and fingerprint to its generated lock artifact. Those are export concerns and do not need to widen the base registry config initially.

Component-level config

final class DesyComponentCatalogConfig {
  const DesyComponentCatalogConfig({
    this.include = true,
    this.description,
  });

  final bool include;
  final String? description;
}

Normal component description remains the default. The component config exists for the exceptions Desy cannot derive and should stay smaller than the component declaration it qualifies.

Why instance swapping remains the slot model

A component child is already represented by widgetInstance. The compiler only needs to interpret that knob as a structural component reference rather than a string. The plural form covers explicit lists.

Desy declarationGenerated meaning
widgetInstanceOne component reference
widgetInstancesExplicit list of component references
Allowed registry instancesDerive allowed owning component types where validation supports it

The adapter must generalize widget resolution: Desy resolves registry instance IDs, while GenUI resolves surface-local component IDs. This is a resolver boundary, not a second composition API.

What the event knob owns

Desy ownsApplication/backend owns
Event knob ID and descriptionAction name and application meaning
emit() and optional JSON payload forwardingPayload definition and validation
Callback bridge used by the real widgetUser, tenant, and object authorization
Safe preview emitterSide effects, tools, persistence, and retries
Generic catalog action schema mappingTransport-specific action/context encoding

An event knob is necessary because a config-only event cannot reach a real widget’s onPressed or equivalent callback without wrapping or approximating that widget. Desy does not interpret a payload: it carries an optional JSON-safe object in a protocol-neutral event invocation, and the adapter/backend owns its contract.

Potential event shape

final submitted = knobs.event(
  'submitted',
  description: 'Emitted when the current value is submitted.',
);

// Common case: the A2UI action already contains all required context.
onPressed: () => submitted.emit(),

// Escape hatch: the widget collected a value locally.
onSubmitted: (text) => submitted.emit({'text': text});

The event definition remains generic in the generated catalog. Desy does not add a payload schema, codec, or business event registry. The host receives a DesyEventInvocation containing the event definition, protocol-owned action value, and optional JSON payload. A GenUI adapter maps that invocation to its outgoing action format; the backend rejects payloads that do not match the selected action’s own contract.

Follow-on possibility: compose a complete chat app from Desy instances

The catalog compiler can become the foundation of a small optional chat host without making Desy an agent framework. A consumer creates ordinary Desy components and named instances for the chat shell, user message, assistant message, composer, pending state, and error state. A validated chat recipe assigns those existing instances to runtime roles. The host supplies conversation state and mounts GenUI surfaces into the declared instance graph.

DesyRegistry+ Desy chat recipe+ Agent target+ Authenticated transport→ Composable GenUI chat app

Three replaceable contracts

  1. Catalog: which trusted components the agent may compose, derived from the registry.
  2. Chat recipe: which named instances render stable application chrome and where runtime values enter them.
  3. Transport: where user text and UI events go, and where text/A2UI responses arrive.

A design-system package can supply the registry and one or more chat recipes. An application can reuse them while replacing only the transport or agent backend.

Why a recipe is not a second registry

The recipe defines no components and contains no widget callbacks. It only assigns stable registry instance and knob IDs to a small set of chat roles. Desy validates every reference against the same registry before the host starts. This is a composition manifest over the registry, not another catalog.

The recipe belongs in an optional GenUI/chat package or consumer app. It should not add chat-specific roles to desy_bench core.

Potential chat authoring shape

The recipe uses rich validated role objects rather than a loose map. Each role points back to existing instances and knob definitions; it does not reproduce their component schema.

How one turn composes

  1. The host builds the root shell instance and overrides its plural messages knob with runtime message children.
  2. The composer’s event knob emits submitted text to the host transport.
  3. The backend streams text and validated A2UI messages using the generated catalog.
  4. The host resolves the returned surface as the content child of the assistant-message instance.
  5. An event knob inside generated UI sends its A2UI action back through the same conversation.
  6. The next backend response updates or replaces the surface, advancing the flow.

How far the no-binding version can go

  • Streaming text plus generated assistant cards and layouts.
  • Buttons, choices, confirmations, retry, cancel, and follow-up actions.
  • Guided support, onboarding, discovery, recommendation, and approval flows.
  • Explicit short lists built from multiple child references.
  • Different chat apps using the same design-system registry and different recipes/backends.
  • Domain-level interactive widgets that keep their own temporary state and emit a final event payload.

Where the boundary appears

  • Several independently generated inputs sharing one editable form model.
  • Two-way synchronization between a widget and agent-owned data.
  • Repeated/template children driven by a changing data list.
  • Client functions and cross-component validation.
  • Offline persistence and restoration of a generated surface.

Those needs justify revisiting binding later. They are not required to prove a useful event-driven chat product.

Composable product ladder

1 · CatalogGenerate trusted components and builders from the registry.
2 · One chatUse a fixed consumer shell and render GenUI inside assistant turns.
3 · RecipesSwap named-instance compositions without changing the runtime.
4 · App familyReuse one registry across support, onboarding, sales, or operations agents.

The first proof should stop at level 2. Level 3 is the dream worth preserving in the API: no assumption in the catalog compiler should prevent the host from resolving named instances with runtime knob overrides.

Agent plug-in boundary: one shell, many jobs

A GenUI experience combines one validated Desy shell recipe with one non-secret agent target. The target identifies a job such as support, sales, onboarding, or account operations. The Flutter app always talks to one authenticated application gateway; server-side profiles decide which model, tools, data connectors, and specialist agents perform that job.

Shell instance+ Agent ID+ Catalog ID→ GenUI experience

Flutter owns safe experience selection

  • Stable experience ID and visible name.
  • Root shell/chat recipe.
  • Non-secret gateway agent ID.
  • Expected catalog ID and fingerprint.
  • Application session token provider.
  • Conversation lifecycle, cancellation, and local presentation state.

The Flutter configuration never contains provider keys, tool credentials, database connections, or model prompts that must remain private.

Backend owns the agent profile

  • Model/provider selection and fallback policy.
  • System instructions and job-specific behavior.
  • Tools, MCP servers, APIs, databases, and remote A2A agents.
  • User, tenant, and object authorization.
  • Conversation storage and handoff policy.
  • Catalog loading, prompt assembly, output validation, retries, and audit.

Several backend implementations may serve the same agent ID during evaluation, provided they emit the same validated text/A2UI contract.

The experience belongs to the consuming application or optional GenUI package, not the design-system registry. It joins presentation and behavior without making either side own the other.

Framework-neutral transport

abstract interface class GenUiAgentTransport {
  Stream<GenUiAgentEvent> send(
    GenUiAgentRequest request,
  );

  Future<void> cancel(String requestId);
}

An A2A connector, custom authenticated SSE connection, WebSocket, or test fixture can implement the same boundary. The chat shell and registry compiler never depend on Dartantic, ADK, Flue, Go, or a particular provider SDK.

Backend pattern A: direct UI agents

Each job-specific agent receives the catalog and emits A2UI directly. This is the shortest path for independent agents and makes it easy to compare frameworks.

  • Simple ownership and deployment.
  • Each agent needs catalog prompting and validation.
  • Handoffs must preserve conversation and surface identity.
  • UI quality may vary between agent implementations.

Backend pattern B: specialists plus UI composer

A router or primary agent calls domain specialists that return structured results. One presentation agent translates those results into the selected catalog and passes them through a single validator.

  • Specialists do not need to understand A2UI.
  • One place owns catalog compatibility and UI quality.
  • Remote systems remain tools or A2A agents behind the gateway.
  • More orchestration, but cleaner multi-agent growth.

Recommendation: use direct UI agents for the first comparison, then converge on a UI composer when several specialists share one product surface.

Recommended backend topology

Flutter experience→ Auth + agent gateway→ Agent router/profile→ Specialists + connectors→ UI composer→ Catalog validator→ A2UI stream

The gateway is the security and compatibility choke point. It negotiates a known catalog, scopes every connector to the authenticated actor, namespaces surface IDs across handoffs, validates output, and prevents the client from following arbitrary agent-supplied endpoints.

Agent discovery and handoff

The first release should use application-declared agent IDs. Dynamic agent cards or A2A discovery may exist behind the gateway, but the client should not discover and connect to arbitrary remote agents directly.

A handoff keeps the same gateway conversation while the server changes the active profile or delegates work. The app may display the new agent identity, but authentication, credentials, and routing stay server-owned.

Catalog compatibility

Every request advertises the client’s supported catalog ID and fingerprint. The selected agent profile names the server-known catalog it was prompted and validated against. A mismatch fails before a model call or falls back to plain text; the backend never trusts an arbitrary inline catalog uploaded by the client.

Different agents can share one full design-system catalog initially. App-specific catalog projections can follow only if prompt size or capability control proves it necessary.

Generated outputs

  • A Flutter Catalog whose items build real registry widgets.
  • A standalone catalog.json containing the matching component schemas.
  • A catalog.lock.json with catalog ID, version, protocol version, and deterministic fingerprint.
  • Optional prompt examples derived from named component instances.

The app may compile the Flutter catalog directly from its live registry. For production, the matching backend JSON should be generated and promoted by the repository build rather than trusted as an arbitrary runtime upload.

Validation and acceptance

  • A registry without catalog config has no behavior or declaration changes.
  • Equivalent registries produce byte-stable catalog JSON and fingerprints.
  • Every emitted component schema has a matching real-widget builder.
  • Single and multi-instance knobs render the same component graph in Desy and GenUI fixtures.
  • Event knobs dispatch through a fake host in tests without embedding business logic.
  • Payload-free and JSON-payload event invocations remain observable in Desy without interpreting their business meaning.
  • Named-instance examples validate against the generated catalog.
  • Unsupported declarations produce an explicit compiler issue rather than a partial silent export.

Workability decision

Yes: the settled v0 registry contract is sufficient to generate and render a useful interactive catalog. It can describe literal string, number, and boolean properties; explicit single and multiple component children; generic actions with optional opaque JSON payloads; real Flutter builders; themes; and instance-derived examples. That is enough for generated text, cards, layouts, choices, confirmation actions, and event-driven chat turns.

It is intentionally not complete A2UI feature coverage. Data binding, repeated/template children, client functions, and shared editable form state remain deferred without making the catalog invalid or unusable.

What changes in desy_bench

  • Optional registry and component catalog config.
  • Optional descriptions on knob definitions.
  • Plural widget-instance knob and resolved widget list.
  • Event knob and protocol-neutral event host/invocation.
  • A pluggable child resolver so the same component builder can resolve registry instances in Desy or surface-local component IDs in GenUI.
  • Validation for the new knob kinds and deterministic export data.

These are protocol-neutral registry/build contracts. desy_bench does not import GenUI or A2UI types.

What belongs in the optional adapter

  • Translate knob definitions into A2UI JSON Schema.
  • Create one Flutter GenUI CatalogItem per eligible component.
  • Call the existing real-widget buildWithValues path.
  • Resolve A2UI child IDs through the GenUI item context.
  • Map event invocations to A2UI actions.
  • Generate catalog.json, instance-derived examples, and a deterministic lock/fingerprint.
  • Validate generated messages and fixtures against the pinned protocol version.

This likely belongs in an optional package such as desy_genui so the reusable registry remains independent of a changing protocol.

Desy Surface stays separate

DesySurfaceDocument→local prototype preview · A2UI messages→GenUI SurfaceController

Do not translate A2UI through DesySurfaceDocument and do not turn DesySurfacePreview into the production GenUI renderer. The formats have different responsibilities: Desy Surface is a nested, local composition prototype; A2UI is an adjacency-list protocol with surface lifecycle, data, and actions. Using Desy Surface as an intermediary would be lossy and would create a second runtime.

Surface model changes

No format or version change is required. Existing component nodes and JSON-compatible knob overrides remain sufficient for local prototypes. Callbacks and protocol actions must not be serialized into a Desy surface.

Surface compatibility work

The validator and preview build environment must understand the new declarations so exhaustive knob switches continue to work:

  • Validate plural instance values as lists of registered instance IDs when used in a local Desy surface.
  • Supply a preview/no-op event host; reject serialized event overrides rather than persisting callbacks or protocol actions.
  • Continue resolving local instance swaps through the registry resolver.

This is compatibility plumbing around the existing surface, not a new surface capability.

Non-goals

  • No data-binding declaration or two-way input synchronization in the first slice.
  • No restricted-string/enum knob expansion solely for GenUI.
  • No object, arbitrary list, nullable, or general JSON-schema knob system.
  • No repeated/template child lists; only explicit component references.
  • No client-function catalog.
  • No Desy-owned schema, codec, or validation language for optional event payloads.
  • No business logic, agent framework, provider keys, or backend in Desy.
  • No agent endpoints, tool credentials, model prompts, or connector configuration in DesyRegistry.
  • No second component inventory, surface DSL, or generated production Dart widgets.
  • No required handwritten model examples.
  • No general chat framework in the catalog-compiler MVP; the composable chat host is a dependent optional experiment.

Open questions

  • Should all representable components be included by default, or should a component-level config be an explicit opt-in? The recommendation is default inclusion to avoid boilerplate.
  • Under the component-first decision, should a static component with several fixed instances be excluded, emit only its default, or use a narrowly documented exception?
  • How should a protocol adapter combine its action-defined context with an optional widget-emitted payload without making that merge policy part of Desy?
  • Should knob descriptions appear inline in the control panel, through help affordances, or both?
  • Does the first adapter belong in an optional package such as desy_genui, or can the protocol-neutral compiler live beside the experimental export?
  • When should one-way scalar binding be added automatically, without expanding registry declarations?
  • Can a chat recipe identify runtime knob ports ergonomically without code generation or fragile string conventions?
  • Should recipes live in consumer Dart code only, or eventually become validated serializable manifests containing registry IDs and values?
  • Does the first backend contract use the bundled A2A connector or an application-owned authenticated SSE transport?
  • Should an experience permit direct selection among several agent IDs, or should routing remain entirely server-side?
  • What minimal metadata may describe an agent to the user without exposing server configuration?
  • When several specialists contribute to one turn, does the primary agent or a dedicated UI composer own the final A2UI surface?

Do or don’t?

Do as a narrow optional compiler proof, after the registry contracts are stable enough to absorb descriptions, plural instance resolution, and an event bridge. Impact 4/5, complexity 3/5, risk 3/5, yield 1.33. The reward is real—one consumer-owned declaration can serve the workbench, Flutter renderer, and multiple agent backends. The main risk is allowing protocol completeness to turn knobs into a general schema language. Hold the first slice to one catalog item per component, literal scalar values, explicit component references, generic actions, and opaque optional JSON payload forwarding; refuse bindings, functions, payload-schema authoring, and application logic until usage proves they belong.
