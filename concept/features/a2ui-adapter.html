Archived interoperability research

A2UI is not part of the chosen real-Dart Workshop.

This page preserves protocol research only. The Registry Spine works on ordinary Flutter source and does not require a generated UI catalog or manifest renderer.

Reason and user value

A2UI’s catalog model closely matches Desy: trusted client-owned components, declarative agent output, schema validation, and native rendering. Desy can remove the duplicate work of manually authoring an A2UI catalog beside a Flutter design-system registry.

Scope

  • Optional desy_a2ui package, never a core dependency.
  • Export a freestanding A2UI catalog JSON Schema from eligible registry components.
  • Map serializable knobs to component properties and legal references.
  • Translate supported A2UI component updates into DesySurfaceManifest.
  • Render with real registered widgets under the host theme.
  • Pin supported A2UI versions and ship conformance fixtures.

Boundary

DesyRegistry→A2UI catalog adapter→Agent-generated A2UI→Protocol validator→DesySurfaceManifest→Real widgets

Non-goals

  • No replacement of A2UI’s protocol, data model, or version negotiation.
  • No arbitrary server-supplied component implementation.
  • No automatic exposure of every registered component.
  • No functions/actions in the first interoperability slice.
  • No promise that Desy-specific surfaces are portable to non-Flutter catalogs.

Implementation sketch

  1. Define eligibility: only components whose knobs are fully serializable.
  2. Create explicit mapping for IDs, properties, defaults, descriptions, and theme capabilities.
  3. Bundle a standalone catalog with a stable catalog ID and registry fingerprint.
  4. Implement static create/update component messages before streaming and data binding.
  5. Translate supported layout/components into the canonical manifest.
  6. Test against official A2UI examples and evolving v0.8/v0.9 fixtures.

Open questions

  • Should Desy export custom components directly or wrap the A2UI Basic Catalog?
  • How are component-slot references represented in A2UI schemas?
  • What happens when a registry changes without a new catalog ID?
  • Which functions and events can the host safely expose?
  • Should a surface retain its original A2UI payload for debugging?

Do or don’t?

Don’t plan this now. It depends on the surface-manifest direction Desy has explicitly left behind. Revisit only if a concrete external interoperability request justifies a separate adapter package without changing the Registry Spine workflow.

Decision: archived research. No A2UI adapter belongs in the current Registry Spine plan.
