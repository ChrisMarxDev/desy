Architecture · one declaration, several execution contexts

Make the registry the kernel, not the workbench the container.

A consumer should declare its Flutter design system once, then let the workbench, screenshot tools, golden tests, catalogue exporters, GenUI adapters, and a future server-driven runtime consume that same live graph. Desy should separate the registry contract from every capability without pretending the widget-returning registry is serializable or runnable in a plain Dart VM.

Consumer widgets→one DesyRegistry→live Flutter tools + derived portable artifacts

Reason and user value

Desy already captures stable identities, real widget builders, themes, typed parameters, named instances, scenarios, composition references, and events. Reusing that declaration can remove repeated setup across visual testing, documentation, agent UI, and application runtimes while guaranteeing that rendered output still uses production widgets.

Decision

Extract a Flutter-native registry kernel and keep capabilities optional. Add optional protocol-neutral DesyRegistryIdentity(id, version) to name that one registry for portable artifacts, replacing agent-specific DesyCatalogConfig. Offer a cohesive workbench and CLI experience on top, but do not make the workbench package own every runtime.

The arrows describe consumption, not ownership. The consumer continues to own the production widgets, theme wrappers, and registry. Desy packages provide typed ways to inspect, compile, render, or test that graph.

desy_core

  • DesyRegistry, themes, typed atom lanes, components, knob definitions, instances, scenarios, events, and widget resolver.
  • Immutable construction, stable-ID validation, cycle checks, and canonical ordering helpers.
  • An optional DesyRegistryIdentity and deterministic, callback-free registry snapshot/digest for tools that need portable metadata.
  • Flutter SDK dependency only where practical; no routing, persistence, Forui, window management, workbench state, GenUI, HTTP, or test runner.

desy_bench

  • The cohesive local design workspace, Registry Spine, preview shell, routing, session state, and extension hosts.
  • Depends on desy_core and Desy's private scaffold package.
  • May present results from optional capabilities through adapters, but does not implement their engines.
  • Remains useful with only a minimal registry and no advanced packages.

Capability packages

  • desy_goldens: automatic plan, Flutter test harness, comparison, and receipts.
  • desy_genui: schema compiler, A2UI/GenUI adapter, action bridge, and client surface.
  • desy_screenshot_builder: interactive workbench extension.
  • A future docs/CMS exporter: static registry facts and examples, not a CMS product.
  • A future desy_sdui: validated client manifest runtime only after a real application proves its requirements.

Flutter command runner

  • Runs through Flutter’s supported headless test boundary, forwards output and exit codes, and locates receipts.
  • Provides commands such as desy goldens verify and desy catalog build.
  • Does not dynamically load consumer libraries, copy registry data, or become a second plugin registry.
  • Uses the widget-test engine for headless registry execution and rendering.

One consumer setup, not one giant package

// package:acme_desy/acme_desy.dart
final acmeRegistry = DesyRegistry(
  name: 'Acme',
  identity: const DesyRegistryIdentity(
    id: 'acme.design-system',
    version: '1.0.0',
  ), // Optional: required only for portable artifacts.
  themes: [...],
  components: [...],
);

// tool/desy_driver_test.dart — one compile-time Flutter bridge
void main() => runDesyToolchain(registry: acmeRegistry);

The API names are conceptual. The important boundary is one type-checked import anchor, not one target per component or capability. The CLI can scaffold and invoke this bridge, but it cannot eliminate the bridge: Dart has no safe runtime mechanism for a command package to import an arbitrary consumer symbol, and the registry itself requires Flutter.

Consumers with one app may keep the registry beside that app. Teams sharing one design system across several apps should place the declaration in a narrow integration package that depends on their production component packages and desy_core. Desy should recommend this shape without requiring a package split for small projects.

Two outputs from one source

FormContainsUsed by
Live DesyRegistryReal widget/theme builders, typed runtime values, resolvers, scenarios, and callbacks.Workbench previews, Screenshot Builder, golden rendering, GenUI/SDUI client rendering.
Derived registry snapshotStable IDs, names, descriptions, schemas, legal values/slots, examples, versions, sources, and a deterministic digest—never widgets or callbacks.Backend compatibility checks, agent prompts, static documentation, catalogue search, CMS integration tooling, and receipts.

The snapshot is a generated artifact, not a second declaration. A backend can understand what the shipped client supports, but only the client containing the live registry can turn a component ID into a Flutter widget.

Server-driven UI boundary

registry snapshot + digest→trusted server composer→versioned surface manifest→client validation→live registry resolution
  1. The application ships production widgets and the live registry. No server downloads Dart or widget code.
  2. A build step publishes the callback-free capability snapshot to the server.
  3. The server returns a declarative tree or protocol message containing component IDs, literal typed values, legal child references, and named actions.
  4. The client checks schema version, registry/catalog digest, maximum depth/node count, allowed components, every value constraint, every slot, and every action binding before rendering.
  5. The client resolves nodes through the shipped registry and applies the real theme once around the surface.
  6. The host application maps allow-listed action IDs to authenticated business behavior. Desy never accepts remote callbacks, arbitrary Dart, navigation commands, URLs, or application services.

GenUI/A2UI is the best current proving ground because the repository already has a compiler and client renderer. A separate product-controlled SDUI protocol should not be invented until GenUI exposes a concrete missing requirement.

What blogging and CMS reuse means

Desy can export design-system capability and resolve trusted content blocks to real widgets. It should not become a content database, publishing workflow, router, SEO system, rich-text format, or media pipeline. A CMS adapter owns content schemas and maps its finite block vocabulary to registered component IDs and values.

What “out of the box” means

The workbench should offer a polished default experience and surface installed extensions. The CLI should offer a consistent command family. Neither should force every consumer to ship golden tooling, GenUI runtimes, server protocols, CMS adapters, or their transitive dependencies.

Scope

  • Extract and stabilize the Flutter-native desy_core package.
  • Replace DesyCatalogConfig with optional generic DesyRegistryIdentity and define one deterministic portable snapshot/digest contract.
  • Derive every capability from every registered component; reserve any future delivery-only redaction for outside the registry and never a parallel component inventory.
  • Define one scaffoldable consumer Flutter bridge for CLI commands.
  • Migrate GenUI and goldens away from workbench dependencies.
  • Document which packages run in plain Dart, headless Flutter tests, interactive Flutter apps, and external servers.

Non-goals

  • No pure-Dart rewrite of widget-returning registry contracts.
  • No dynamic plugin discovery or reflection over consumer libraries.
  • No single serialized representation that must serve goldens, A2UI, CMS content, and local prototypes.
  • No requirement that every registry opt into remote or generated UI.
  • No workbench dependency on every optional capability.
  • No server, account, hosting platform, remote code loading, or business-action framework in the architecture slice.

Implementation sketch

  1. Freeze the seam. Inventory every public registry type used outside workbench presentation and add dependency-boundary tests.
  2. Extract without redesign. Move registry declarations, validation, resolution, and the neutral missing-instance fallback to desy_core. Keep compatibility exports from desy_bench during migration; move no workbench routing, extension host, or Desy-owned scaffold UI.
  3. Move portable derivation. Replace DesyCatalogConfig with optional DesyRegistryIdentity; then replace the workbench-owned experimental catalogue export with a canonical snapshot builder and digest beside the registry kernel. Do not add capability-specific fields for goldens, CMS, or protocols.
  4. Migrate proven consumers. Point desy_goldens_prototype and desy_genui at desy_core. Keep Screenshot Builder on the workbench extension interface.
  5. Productize command execution. Evolve the golden prototype's two-process shell into a Flutter command family that invokes one configured flutter test bridge and writes typed receipts under .dart_tool. Do not present it as a dart run command.
  6. Prove external reuse. Generate a static catalogue artifact and run the GenUI client from the same dogfood registry. Confirm identical IDs and digests across both outputs.
  7. Gate SDUI. Only start a separate runtime spike when one real application supplies transport, compatibility, offline, action, and security requirements not already answered by GenUI.

Acceptance criteria

  • A minimal consumer registry still launches the workbench unchanged.
  • GenUI and golden packages no longer depend on workbench routing or scaffold UI.
  • Every generated artifact carries one canonical registry identity/version and digest.
  • Adding a component automatically affects goldens and catalogue exports without another target declaration.
  • The CLI can run from a terminal but all registry evaluation and rendering occurs inside Flutter.
  • An optional capability can be removed without changing the registry's widget inventory.

Open questions

  • How should a host report a missing identity when a selected portable capability requires one: a direct compile error, or a CLI setup hint that can scaffold it?
  • Does the CLI scaffold one generic Flutter bridge or one test bridge per capability package?
  • Which metadata is a universal component fact, and which belongs only in sparse GenUI, golden, documentation, or SDUI policy?
  • Should compatibility exports remain in desy_bench for one release or require a coordinated breaking migration?
  • What first production application would justify reviving the parked SDUI runtime?

Do or don’t?

Do the registry-kernel extraction; do not build the universal platform yet. Impact 5/5, complexity 4/5, risk 3/5. GenUI and goldens already provide two registry-only consumers, so the smaller dependency boundary is earned rather than speculative. The main risk is turning a useful seam into a plugin framework or serialized widget language. Keep capabilities explicit, Flutter-native where widgets are involved, and portable only at the derived metadata/manifest boundary.

Decision: one live Flutter registry, one optional consumer integration library, several narrow capability packages, and a CLI that orchestrates Flutter rather than replacing it.
