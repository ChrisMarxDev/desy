Select anything visible. Say what should change.

Lift the proven render-object picker into the Registry Spine shell so Home, Atlas, detail views, generated candidates, and Desy’s own chrome share one source-aware annotation workflow.

Reason and user value

“The spacing feels wrong” is weak agent input when four candidate widgets are visible. A comment attached to the exact Text, Column, or consumer component gives the agent a concrete target while preserving the visual context that made the problem obvious.

Scope

  • Start inspection from one persistent top-bar action on every workbench screen.
  • Capture current screen or artifact identity, widget and render-object types, source location, ancestry, logical bounds, active theme, viewport, and scroll state.
  • Show Desy signal-pink selection, a numbered pin, and one bottom-center composer.
  • Support multiple collapsed annotations and include them in the current agent turn.
  • After hot reload or navigation, re-resolve the target with an explicit detached state when confidence is low.
  • Later enrich accepted annotations with screenshot evidence and a verification receipt.

Non-goals

  • No promise of a permanent DOM-style selector for arbitrary Flutter trees.
  • No serialization of live Element or RenderObject instances.
  • No issue tracker or account system in core.
  • No autonomous patch execution merely because a comment exists.
  • No universal “resolved” state without consumer-owned persistence.

Implementation sketch

  1. Keep one versioned DesyWidgetTarget containing screen or artifact identity, source evidence, widget ancestry, and logical bounds.
  2. Move discovery, hit testing, and outline painting into a shell-owned debug inspector service.
  3. Let every routed surface register inspectable roots without owning annotation state.
  4. Store annotations in the active session and workspace focus, never the registry.
  5. Render pins before presentation transforms and pair every comment with exact target evidence in the next turn.
  6. On reload, resolve targets best-effort and require human reattachment for ambiguous matches.

Smallest useful flow

Inspect widget→Add comment→Review pins→Send structured feedback→Hot reload→Reattach or verify

Acceptance criteria

  • A comment names the candidate and project widget rather than only screen coordinates.
  • Its visible pin aligns with the selected widget at the candidate’s intended preview geometry.
  • The agent prompt contains the human comment, source evidence, widget ancestry, and candidate ID.
  • Hot reload never silently moves an annotation to a low-confidence target.
  • Users can continue without persistence or an external task system.

Open questions

  • Is source file and line sufficiently stable across an agent edit, or should generated candidate widgets receive explicit keys?
  • Should a comment attach to one widget, a rectangular region, or both?
  • Does annotation selection block interaction with stateful candidate widgets?
  • Which target evidence is safe and useful to retain in repository-local session history?
  • What confidence threshold should require manual reattachment after reload?

Do or don’t?

Do the shell-owned slice now. Impact 5/5, complexity 3/5, risk 2/5, yield 1.67. Candidate inspection already proves the primitive. Making it global turns the chosen interface into a tool that can improve both consumer widgets and Desy itself.

Decision: enrich the existing extension boundary; do not add a second task system.
