Reason for existing

For design-system authors

Make the contracts, states, semantics, and token usage of real components easy to inspect and evolve.

For product builders

Compose screens from approved capability, responsive patterns, and representative data without re-deciding every visual primitive.

For agents

Offer a precise local query surface and verification loop so an agent can select real widgets and prove the result.

The separation

System authors
tokens · themes · components · contracts→Desy registry
typed, executable source of truth→Screen designers / agents
recipes · compositions · evidence→Flutter app
reviewed production code

A screen composition may reference registered IDs and serializable values. It must never become a parallel home for business logic, callbacks, arbitrary styling, or a replacement component implementation.

Primitive foundations first

These are the essential building blocks of a serious Flutter design system. They precede screen composition and agent workflows; Desy should expose them as optional typed adapters over widget-returning primitives, never force a visual language.

F1 · Numeric values: spacing, size, radius, and duration

Impact 5 · Complexity 2

Add typed numeric entries with a unit, semantic name, display format, and visual specimen. This unifies spacing, sizing, border radius, icon size, stroke width, breakpoint values, and animation durations without turning every number into a special model.

F2 · Typography roles and text specimens

Impact 5 · Complexity 2

Represent named text roles with real Flutter text builders, font details, line-height, fallback behavior, and long-content specimens. Show roles in context rather than treating a font family as sufficient documentation.

F3 · Semantic color roles, themes, and modes

Impact 5 · Complexity 3

Expand the current color atlas into semantic roles, raw palettes, aliases, and theme-specific values. Show contrast and real surface context; retain the consumer theme wrapper as the runtime authority.

F4 · Motion tokens and animation specimens

Impact 5 · Complexity 3

Catalog named durations, curves, delays, and motion intents such as enter, exit, emphasis, and feedback. Let a consumer supply a live widget specimen so Desy can preview real movement without owning an animation framework.

F5 · Icons, illustrations, and asset contracts

Impact 4 · Complexity 3

Make approved icon names, sizing, semantic labels, color behavior, and asset variants discoverable. Begin with widget-returning entries and source links; avoid a second asset pipeline or binary store.

F6 · Surfaces, borders, and elevation treatments

Impact 4 · Complexity 2

Expose the visual treatments that make components feel coherent: fills, borders, opacity, shadow/elevation, blur, and shape. A treatment is previewed as the consumer’s real widget, not recreated as a generic Desy card.

F7 · Layout primitives and responsive thresholds

Impact 5 · Complexity 3

Document approved page gutters, content widths, grids, gaps, safe areas, and breakpoints. Show each at representative device widths so designers can use the system’s layout vocabulary before composing a screen.

F8 · Interaction states as first-class primitives

Impact 5 · Complexity 3

Define hover, focus, pressed, selected, disabled, loading, and validation behavior as inspectable states across components. This is where a polished system becomes implementable rather than merely attractive.

F9 · Content rules and overflow specimens

Impact 4 · Complexity 2

Capture practical content limits, capitalization, truncation, localization expansion, and empty-state expectations beside components. Preview short, long, missing, and translated strings with consumer-owned fixtures.

F10 · Primitive coverage map

Impact 4 · Complexity 3

A simple matrix shows which components consume which colors, text roles, spacing, motion, icons, and states. It reveals orphaned values and hard-coded gaps without pretending to fully infer design intent.

Agent and composition ideas — after the vocabulary

Scores are initial product-owner estimates: impact / complexity on a 1–5 scale. They are prompts for a decision, not commitments.

01 · Local registry query for agents

Impact 5 · Complexity 2

A small local interface answers: “Which components accept a trailing action?”, “What is the approved destructive action?”, “Show the properties and slots of Card.” It returns typed, compact results with source links—not a giant Markdown dump.

02 · Task-sized agent context packets

Impact 5 · Complexity 2

Generate a focused, machine-readable packet for a task or screen: relevant themes, tokens, components, contracts, examples, and verification commands. This follows minimum necessary declaration at the context level.

03 · Component contract inspector

Impact 5 · Complexity 3

Turn each real widget into an inspectable contract: typed properties, legal slots, defaults, states, semantics, source location, related components, and examples. This is Desy’s equivalent of Figma’s component playground—backed by executable Flutter.

04 · State matrix and interaction stories

Impact 5 · Complexity 3

Capture loading, disabled, focus, validation, empty, overflow, and error states as named scenarios. Agents can choose and test a state rather than inventing one from a default preview.

05 · Accessibility evidence panel

Impact 5 · Complexity 3

Show semantics, keyboard traversal, text-scale behavior, contrast checks, and author-supplied accessibility guidance beside each component and scenario. Start as evidence and warnings, not a pretend universal accessibility score.

06 · Token modes and alias graph

Impact 4 · Complexity 3

Make theme values, aliases, and raw values traversable: “surface.positive → green.500” across Daylight, Midnight, and future brands. Figma’s variable modes are useful inspiration; the Flutter theme remains authoritative.

07 · Responsive and environment matrix

Impact 5 · Complexity 3

Run the same component or screen through device size, text scale, locale, directionality, theme, and platform inputs. Save known-good environments as named scenarios agents can invoke.

08 · Scenario runner with visual evidence

Impact 5 · Complexity 4

Render registered scenarios deterministically, keep goldens, and report a focused diff. An agent’s handoff includes the exact scenario names and proof that the target states passed.

09 · Screen recipes, not freeform screens

Impact 4 · Complexity 3

Provide reusable product patterns—settings, form, list-detail, onboarding, empty state—with named regions and constraints. A recipe is a composition guide and starter manifest, never a new visual component system.

10 · Declarative composition manifests

Impact 4 · Complexity 4

Allow a Bench user or agent to save a screen composition of registered IDs, legal slots, and serializable values. Render it locally for review; keep callbacks, business logic, and production-code generation out of the manifest.

11 · Typed preview fixtures

Impact 4 · Complexity 3

Let consumer-owned, typed fixtures provide realistic names, long strings, zero states, permissions, and failure data. Agents select fixture IDs, never fabricate fragile UI data in prompts.

12 · System health and adoption lens

Impact 4 · Complexity 4

Find raw values where semantic tokens exist, deprecated component use, unexercised states, and missing scenario coverage. Begin with static registry and project analysis; do not add surveillance analytics or a hosted dashboard.

13 · Component lifecycle and migration guidance

Impact 4 · Complexity 3

Record experimental, stable, deprecated, and replacement relationships in the registry. Give agents an actionable migration path rather than a vague warning.

14 · Evidence links to source, tests, and docs

Impact 4 · Complexity 2

Every registry item can expose optional local links to its Dart source, tests, usage guidance, and issue context. Inspired by Figma Dev Mode resources, but repository-native and offline-first.

15 · Agent design-review gate

Impact 5 · Complexity 4

Before a change lands, compare its widget tree, selected components, token usage, semantics, and scenario evidence against the registry. Produce review findings with concrete replacements, not aesthetic opinions.

16 · Figma import or continuous sync

Impact 2 · Complexity 5

Useful only if a team already treats Figma as the source of truth. For Desy’s repository-owned model, it risks creating competing definitions and conflict resolution work.

17 · Freeform pixel canvas

Impact 1 · Complexity 5

A Figma-like editor would be impressive but undermines component contracts and turns Desy into a parallel app builder. It conflicts directly with the source-of-truth and compose-before-configuring principles.

18 · Automatic production Dart generation

Impact 2 · Complexity 5

Potentially useful much later, but risky before composition contracts and application ownership are proven. Desy should first make agents faster at producing reviewed normal Flutter code.

Scope for the next coherent release

Strong default

  • Numeric values, typography roles, color modes, and treatments
  • Motion, icon/asset, layout, and responsive primitives
  • Interaction and content-state specimens
  • Primitive coverage before broad component tooling

Sequence later

  • Component contracts and typed preview fixtures
  • Environment matrix and deterministic scenario evidence
  • Local query and task-sized agent context packets
  • Screen recipes, manifests, and an agent review gate

Non-goals

  • A competing design-system source of truth, hosted asset library, or Figma clone.
  • Arbitrary visual overrides, freeform pixel layout, or a general no-code app builder.
  • Serializing callbacks, business logic, navigation, secrets, or application state into screen manifests.
  • Automatic production Dart generation before the normal source-and-review loop is demonstrably improved.
  • Forcing consumers to write verbose schemas when rich typed objects can provide the same information.

Implementation sketch

DesyRegistry → typed primitive adapters → live specimens → component contracts → scenarios → local query / packet exporter → evidence → agent review

Extend the existing widget-returning registry in layers. A consumer with colors and fonts already gets an Atlas; it can opt into numeric, motion, assets, or layout values independently; components later reference those entries where useful; agent context is derived only from the selected, living system.

Open questions

  • Which numeric groups deserve dedicated adapters first: spacing, radius, duration, breakpoints, or all of them?
  • Should motion be organized by physical values (duration/curve) or semantic intent (enter/emphasis/exit), or both?
  • How do we expose layout rules without trying to replace Flutter’s own layout model?
  • What is the smallest component contract object that adds value without duplicating widget implementation?
  • When the primitive system is ready, should agents query it through a Dart API, CLI, MCP server, generated files, or a deliberately small combination?
