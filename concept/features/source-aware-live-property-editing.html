Rank 18 · Real-Dart experimentation

Try an undeclared widget property against the real source before deciding it deserves a knob.

A reviewer selects a real consumer widget, sees a small set of safely understood constructor arguments, changes a temporary source-backed draft, and evaluates the hot-reloaded result. Accepted changes remain ordinary reviewable Dart diffs; nothing mutates the registry or a live widget instance.

Impact 4/5Complexity 5/5Risk 4/5

Reason and user value

Knobs are the intentional, durable way to expose meaningful variation. Before an author knows which variation matters, however, declaring a knob can be premature. This tool would shorten the question “what if this padding, label, color, or radius changed?” while keeping the answer grounded in the consumer’s actual Dart and theme.

Smallest useful slice

From a selected registry preview, resolve one source constructor invocation, expose only supported literal arguments, apply one ephemeral local source patch, hot reload, and show the exact diff for explicit accept or discard. Begin with strings, booleans, numbers, colors, EdgeInsets, and BorderRadius.

Scope

  • Debug-only selection of real consumer preview content and source-aware targeting.
  • AST-based recognition and editing of a narrow, documented set of constructor-argument expressions.
  • Temporary local draft patches, hot reload, rollback, and an ordinary source diff.
  • Clear distinction between a temporary property experiment and an authored typed knob.
  • An opt-in local host or workspace extension that owns filesystem writes and the resident Flutter tool.

Non-goals

  • No reflection-based mutation of a mounted Flutter widget; widgets remain immutable.
  • No arbitrary Dart-expression editor, general-purpose IDE, or visual/no-code widget language.
  • No registry mutation, second component catalogue, source generation, cloud service, or automatic commits.
  • No editing of Desy scaffold chrome, callbacks, controllers, application state, or unsupported expressions.
  • No promise that every runtime-selected widget maps unambiguously to an editable constructor call.

Implementation sketch

  1. Reuse the scoped preview selection/annotation boundary to retain stable registry identity and source evidence; never keep a live Element as persisted state.
  2. A trusted local host resolves the selected source location, parses the owning Dart file, and finds one supported constructor invocation.
  3. Convert only recognized literal expressions into typed editor fields. Display all other arguments read-only with a reason.
  4. Write a reversible draft patch outside the immutable registry declaration model, invoke the resident Flutter tool’s hot reload, and surface compiler errors as a failed experiment.
  5. Let the user accept the patch into ordinary source or discard it. On acceptance, suggest—but never require—promoting repeatedly useful variation to a typed component knob.
  6. Keep the workbench extension bounded: its only durable outputs are normal consumer code and any user-chosen review annotation.

Open questions

  • How reliably can runtime source evidence resolve a constructor call through composition, builders, and generated code?
  • What patch-isolation method preserves a clean rollback while the developer has unrelated local edits?
  • Which expression forms remain useful without making the editor a partial Dart IDE?
  • Should this begin solely in the dogfood app and desktop debug builds?
  • When should an accepted edit be offered as a candidate knob rather than remaining source-only?

Acceptance criteria

  • A supported argument change visibly rebuilds the real consumer widget under its real selected theme.
  • Unsupported or ambiguous arguments are read-only and explain why.
  • Discard restores the exact prior source state without touching unrelated edits.
  • Accept produces an ordinary, inspectable repository diff and does not change the registry’s identity or inventory.
  • All interactive editor controls are keyboard-operable and scoped away from Desy chrome.

Do or don’t?

Park this until the Registry Spine, source-aware selection, annotation loop, and hot-reload workshop are proven together. The reward is high-quality exploratory design work with less up-front declaration; the risk is equally high because source mapping and reversible editing are fundamentally more complex than live typed knob values. Build only the narrow supported-expression slice when those dependencies have operational evidence.
