The Atlas is home. Workshops are how the system evolves.

Unify Desy’s strongest shipped surface and its hot-reload prototype into one loop: understand the real registry, start an exploration from that context, compare real Flutter implementations, give precise feedback, and watch the same repository update through hot reload.

Browse Atlas→Attach registry context→Workshop real Dart→Hot reload→Review in Atlas

Reason and user value

Flutter developers can already write code and hot reload it, but the feedback loop is fragmented: find an existing component, explain its context to an agent, run the app, compare one result, and repeat. Desy can make the visible design system the working context for that whole conversation.

The differentiator is not an embedded terminal. It is a registry-aware design journey where every proposal is immediately visible under the real theme and remains connected to the components that inspired it.

Product model

  • Atlas is the default home and the map of what exists.
  • Workshop is a separate focused workspace for changing what exists or exploring what comes next.
  • Registry context is passed by stable IDs and resolved live; it is never copied into a second catalogue.
  • Hot reload is runtime infrastructure, not a destination in navigation.
  • Sessions preserve the exploration journey: prompts, candidates, selections, comments, reloads, and accepted direction.

Core UX decision

Do not merge the registry tree and workshop chats into one overloaded sidebar. Atlas keeps the existing registry navigation. Workshop keeps its session-only sidebar. The bridge is contextual: “Workshop this” from an Atlas entry, an “Add from Atlas” picker inside a workshop, and compact context chips above the candidate canvas.

Home is an Atlas overview, not a dashboard

The current Atlas layout stays recognizable. Its registry sidebar remains the navigation source, and the main canvas gains only a thin product layer above the real preview grid:

  1. A quiet status bar names the connected repository, selected theme, and Flutter runtime state.
  2. A single prompt composer asks “What do you want to explore?” and starts a blank or context-seeded workshop.
  3. One “Continue working” row reopens the most recent workshop without turning the page into a task dashboard.
  4. The existing Atlas grid immediately follows and remains the visual center of gravity.

No analytics, setup checklists, registry-health theatre, or vanity metrics. If a section does not help someone browse, start, or resume, it does not belong on home.

The focused workshop

The existing standalone Workshop is the correct shell. Its session-only sidebar remains intact; the body becomes a focused three-layer workspace:

  1. Session header: title, hot-reload state, and a clear exit back to Atlas.
  2. Context strip: attached registry entries, active theme, current preview state, and “Add from Atlas.”
  3. Work area: conversation and activity on the left; a horizontally scrollable rail of described, selectable real-widget candidates on the right.

Candidate selection and later render-object annotations become structured feedback for the next agent turn. The registry enters as context, not navigation clutter.

Scope

  • Make Atlas the root and product home.
  • Show repository, active theme, and Flutter connection state in quiet persistent chrome.
  • Add one start/resume workshop affordance to the Atlas overview.
  • Launch a workshop from a registry entry, instance, or current detail state.
  • Resolve attached context from the live registry by stable ID.
  • Move the proven hot-reload/Codex runtime behind the existing standalone Widget Workshop extension.
  • Render candidates through DesyWidgetPreview with the active consumer theme.
  • Keep workshop sessions ephemeral and repository-local in the first integrated slice.

Non-goals

  • No general-purpose IDE, source explorer, debugger, or terminal product.
  • No second registry owned by desy_ide or the workshop.
  • No automatic registration of experimental candidates.
  • No hosted compilation, multiplayer, accounts, or cloud session storage.
  • No JSON-widget or surface-manifest screen in the primary navigation.
  • No deletion of experimental packages until the unified loop has replaced any useful test coverage.
  • No home-screen analytics or project-management dashboard.

Implementation sketch

  1. Keep DesyBenchApp(registry: ...) as the consumer entrypoint and the one owner of registry validation and workbench session state.
  2. Promote the existing DesyWidgetWorkshopExtension as the focused workspace. It already has standalone presentation, a session-only sidebar, registry access, and the active theme.
  3. Extract the proven process controller and hot-reload boundary from desy_ide into a narrow, desktop-only runtime injected into that extension. Keep desy_ide as a lab until the extraction is stable.
  4. Add a typed optional entry-action boundary so the Workshop extension can contribute “Workshop this” without desy_bench depending on the extension.
  5. Represent a workshop seed with session ID, registry entry IDs, theme ID, preview state, and source paths. Resolve widgets from the registry at render time.
  6. Use ordinary Dart candidate files as the editable boundary. On reload, the Workshop and Atlas both reflect the repository’s real code.
  7. Remove DesySurfaceBrowserExtension from the dogfood app’s primary extension list only after the integrated Workshop is usable; retain the package as a lab or delete it in a separate cleanup decision.

Smallest useful flow

  1. Open Desy into the Atlas.
  2. Open Button and choose “Workshop this.”
  3. A new workshop opens with Button, the active theme, and current preview state attached.
  4. Ask Codex for three alternatives.
  5. Compare real widgets, select one or more, and send feedback.
  6. Codex edits ordinary Dart; Flutter hot reload updates the candidates.
  7. Exit to Atlas and inspect any real registered component changes.

What to remove from the core

JSON widgets, generic AI-prompts placeholders, and overlapping prototype surfaces should leave primary navigation. They dilute the “see the system, workshop the system” story.

What to preserve

Atlas, detail inspection, real theme previews, typed atoms, component paths, session journeys, hot reload, candidate selection, and eventually render-object annotations all strengthen one loop.

What to defer

Session persistence, GitHub snapshots, hosted rendering, multiplayer, agent vendors beyond the local runtime, and candidate promotion should follow demonstrated daily use.

Open questions

  • Should the Atlas composer start a blank workshop, or always require at least one attached registry entry?
  • Does “Workshop this” capture current knob, scenario, device, and viewport state in the first slice?
  • Are candidates session-owned files under a hidden local directory, or normal visible repository files from day one?
  • When Codex changes an already-registered component, should the candidate rail show the modified registry entry automatically?
  • What is the explicit user action that promotes an experimental candidate into the consumer registry?
  • Should Labs exist in the shipped product at all, or only in dogfood/debug builds?

Acceptance criteria

  • A consumer still declares exactly one DesyRegistry.
  • Atlas remains useful without installing or configuring the Workshop runtime.
  • A registry entry can seed a workshop without copying its widget builder.
  • Workshop navigation lists only sessions.
  • Every candidate uses the active consumer theme and real preview geometry.
  • One Codex edit produces a visible hot-reloaded change without relaunching Desy.
  • Returning to Atlas shows repository changes through the same registry declaration.
  • JSON widgets are absent from primary dogfood navigation.

Do or don’t?

Do—this should be the next product slice. Impact 5/5, complexity 3/5, risk 2/5, yield 1.67. The codebase already proves the expensive primitives independently: a registry-driven Atlas, real themed previews, a standalone session-based Workshop extension, a same-process Codex console, and working Flutter hot reload. The remaining risk is product integration and state ownership, not renderer feasibility. Build one entry-to-workshop loop before adding persistence, hosting, or more tools.

Decision: make Atlas + Workshop the core Desy loop. Keep the registry authoritative, keep Workshop focused, and treat the hot-reload runtime as replaceable infrastructure.
