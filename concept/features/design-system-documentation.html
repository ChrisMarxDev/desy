Deferred product decision

Give design systems useful guidance without creating a second knowledge base.

A component catalogue shows the real widget, but teams also need concise guidance: when to use it, constraints, accessibility notes, and examples. Desy should add this only after choosing where that guidance belongs.

Why this exists

Teams otherwise split usage guidance between source comments, a separate documentation site, and verbal knowledge. The registry already names the artifacts that need explanation.

User value

A designer or developer can answer “when should I use this?” beside the real, themed component rather than hunting through a duplicate inventory.

Scope to evaluate

  • Concise authored guidance attached to a registered component or atom.
  • A possible Docs destination for cross-cutting material such as foundations, accessibility, and contribution guidance.
  • One Home/readme entry point that can link to the right guidance without becoming a CMS.

Non-goals

  • No Markdown site generator, backend, account, or collaborative publishing workflow.
  • No second folder tree or duplicate component list.
  • No requirement that a minimal registry provide documentation.

Implementation sketch

First test a small typed guidance value on selected registry entries. Render it in Details beside the live preview. Only introduce a Docs destination if cross-cutting documents cannot remain discoverable from Home and entry details. Any dedicated destination must derive its index from the same immutable registry and avoid callbacks or serialized widget logic.

Open questions

  1. Is entry-level guidance sufficient for the first release?
  2. Which documents are cross-cutting enough to justify a Docs section?
  3. Should Home merely host arbitrary consumer content, or also derive a concise docs index?
  4. What is the smallest typed model that avoids a free-form CMS?

Do or don't

Do: investigate after consumers have proven which guidance is repeatedly needed. Impact is 4/5 and complexity is 4/5: useful, but premature information architecture would create permanent clutter.

Don't: add a Docs sidebar section or component-documentation API now. The right content hierarchy remains unvalidated.

Offline concept artifact. No remote assets or runtime dependencies.
