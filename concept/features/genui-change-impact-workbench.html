Value experiment

Turn a code change into a decision-ready review surface.

The Change Impact Workbench tests GenUI where the question determines the shape of the interface: a code change may need a verification plan, package impact view, migration assessment, or explicit review decision.

Why it exists

Static engineering dashboards either expose every signal at once or require a hand-built page for every investigation. A change-specific review surface should instead prioritize the files, risks, checks, evidence, and decision relevant to one snapshot.

User value

A developer can see what changed, what may be affected, what has been verified, and what decision remains—without relying on prose alone or treating an LLM as the source of repository truth.

Scope

Local sample snapshot→Deterministic review composer→Declared Orbit components→User-owned actions

The first slice provides multiple realistic fixture snapshots, a separate navigation destination, a generated review canvas, focused verification state, and an explicit decision card. It deliberately proves composition before local process execution.

Non-goals

  • No repository write, shell execution, or automated fix.
  • No claim that GenUI replaces normal Flutter coding screens.
  • No provider, authentication, or agent-runtime architecture change.
  • No use of A2UI data-model updates for ordinary app state.

Implementation sketch

  • A typed local change snapshot loader owns fixture data and status transitions.
  • A local composer turns a snapshot into canonical A2UI component operations.
  • The existing catalog renders only registered real Orbit widgets.
  • Generated approval and verification actions return to the app, which decides what state may change.

Experience flow

Choose sample change → inspect impact surface → run focused verification → review evidence → accept scope or request another pass

The snapshot is application data. The generated portion is the temporary arrangement of summary, metrics, verification rows, evidence, and decision controls.

Open questions

  • Which local repository signals merit a production adapter first: diff, analyzer, tests, or package graph?
  • How should source file navigation be represented without giving the model arbitrary filesystem authority?
  • Does deterministic composition remain useful enough before a live Codex driver is connected?

Do or don't

Do the bounded experiment. Impact is high for validating GenUI’s actual role, while complexity is contained because data and actions remain local fixtures. Do not expand to repository execution until people find the composed review surface more useful than a normal static report.
