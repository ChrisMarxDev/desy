ConceptPlanned features

Primitive foundation · measurement board

Let geometry be seen, not merely listed.

Spacing, size, radius, strokes, breakpoints, opacity, and elevation are the physical rules of a design system. A compact token table makes them easy to copy but hard to judge together.

Decision

Do it now. Add one typed numeric primitive with a semantic kind and a dedicated Measurements board. Keep relationships, responsive ranges, and automated token-use analysis as later work.

Why it exists

See rhythm

Compare gaps and dimensions as geometry, rather than memorising a list of numbers.

Keep intent typed

A radius is not just a number. A breakpoint is not just a number. The kind gives the Bench a safe, useful specimen.

Preserve ownership

The consumer still supplies the real specimen when one matters; Desy only visualises the declared primitive directly.

Scope

Typed measure→Direct geometry diagram+Optional consumer widget specimen→Measurements board
  • One DesyNumericEntry with a typed kind: spacing, size, radius, stroke, breakpoint, opacity, or elevation.
  • Small semantic factories for common declarations: .spacing, .size, .radius, and .breakpoint.
  • A dedicated Atom screen, grouped by kind, showing an immediately comparable geometry diagram, value, ID, guidance, and optional real consumer specimen.

Non-goals

  • No new universal token taxonomy or mandatory naming convention.
  • No arithmetic, alias graph, responsive range editor, or bulk token editor.
  • No reimplementation of consumer components: optional specimens remain consumer-owned widget builders.

Implementation sketch

Open questions

  • Should named relationships such as “compact = 2 × tight” be declared when an alias graph arrives?
  • Should layout values gain a device-width comparison board after more consumers demonstrate the need?
  • How should a future validator report a raw literal that duplicates a registered measure?

Risk / reward

Impact 5 / 5Complexity 2 / 5Yield 5 / 5

The risk is accidentally creating a second token system. The narrow typed-kind model avoids that: it describes how to inspect an existing primitive, while the consumer’s numeric value and widget builder remain authoritative.
