Rank 17 · Registry-derived collection canvas

Every collection can become a workspace, without ceasing to be a catalogue.

A folder, atom lane, or component collection should open as a named scene of real registry previews. It begins as a familiar grid, then lets a designer select, move, resize, overlap, inspect, and compare several real widgets in one shared canvas. The shared canvas engine is now used by the component Canvas beta and prototype sessions; its implemented boundary is documented in Collection canvas.

Reason and user value

Catalogue grids are good at browsing one item at a time; detail canvases are good at inspecting one item deeply. Design work often needs both at once: compare a button, badge, field, and feedback state at their real sizes; move them into a relationship; then inspect one of them without losing the rest.

Decision

Make the center surface generic, not every screen canvas-shaped. A sidebar destination resolves a typed collection scene from the one registry. The scene chooses an appropriate initial presentation, while one canvas engine owns pan, zoom, selection, stacking, geometry, and inspector hand-off.

Scope

  • One typed DesyCanvasScene resolved from a sidebar destination and the active registry.
  • Stable scene-item IDs, real-widget builders, a derived initial rectangle, and optional item-specific inspector data.
  • A shared canvas engine for geometry, paint order, selection, zoom, pan, reset, keyboard movement, and accessible item labels.
  • Collection adapters for current component folders and compatible atom lanes. Existing catalogue cards become scene chrome, not a second preview implementation.
  • One selected item opens the existing detail surface; multi-item editing stays in the collection scene.
  • Session-local arrangement only in the first slice. Reloading a registry re-derives unavailable items safely.

Non-goals

  • No general-purpose Figma replacement or freeform screen authoring.
  • No serialised widget tree, callbacks, or application logic.
  • No parallel registry, copied folder inventory, or consumer-declared canvas metadata for ordinary catalogue use.
  • No forced canvas for specialized lanes whose value comes from their existing purpose-built board, such as Measurements or Motion.
  • No permanent persistence, collaboration, or promotion contract in the first slice.

Architecture sketch

DesyWorkbenchNavigationDestination
  → DesyCanvasSceneResolver(registry, destination, activeTheme)
  → DesyCanvasScene(items: immutable DesyCanvasSceneItem values)
  → DesyCollectionCanvas(session-local scene state)
  → real DesyWidgetPreview / existing atom preview builder
  → selection → existing detail inspector or route

The resolver derives scene contents from the existing registry and navigation tree. The canvas owns only ephemeral geometry keyed by stable item ID; it must never become a second declaration source. This reinforces Principles 1, 3, 5, 8, 12, and 13: one registry, real widgets, derived structure, readable scaled previews, rich typed scene values, and composition rather than a flag-heavy gallery API.

Phased rollout

  1. Extract the proven drag-box, geometry, z-order, and zoom behaviour into a private generic canvas primitive. Done: prototype sessions use the typed primitive with host-supplied details builders. The former all-components Canvas beta was removed after validating the shared interaction.
  2. Adapt one component-folder Atlas grid into a scene with deterministic initial placement and reset.
  3. Route selection into the current detail inspector without duplicating knobs or preview construction.
  4. Add compatible atom-lane adapters, keeping specialized boards where a generic scene loses useful meaning.
  5. Only after daily use, decide whether ephemeral arrangements earn a narrow serialisable manifest.

Open questions

  • Should the explicit control say Arrange / Browse, or should every compatible destination open in canvas mode by default with a resettable grid?
  • Which atom lanes preserve enough shared geometry to benefit: Colors and Icons likely do; Fonts, Motion, and Measurements may remain bespoke.
  • Should selection own the right inspector immediately, or should a second click or Enter be required to avoid accidental knob changes while arranging?
  • What minimal scene-state lifetime feels useful: route lifetime, workbench session, or an explicit future saved board?
  • How should a scene announce offscreen selected items and overlapping previews to keyboard and screen-reader users?

Do or don’t?

Do, but start with one collection adapter and no persistence. Impact 5/5, complexity 5/5, risk 3/5, yield 1.00. The reward is a coherent daily workspace that matches how components are compared in practice. The main risk is silently building a second, serialised UI editor. Keep scene items registry-derived, initial layout deterministic, geometry ephemeral, and specialized boards free to remain specialized until a generic canvas is demonstrably better.

Decision: the canvas is a presentation and temporary arrangement of registry-derived real widgets, never another source of system truth.
