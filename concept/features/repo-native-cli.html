Core delivery model

One CLI. One design space per Flutter repository.

Install the tooling once; keep the application’s atoms, components, screens, and generated agent skill under normal version control alongside the app.

Reason for existing

Low ceremony

Run one command from a Flutter repository and get a live workbench. No hosted account, setup server, or detached documentation product.

Ownership

Each app owns its design language in its repository, so it can evolve in pull requests and ship with the code it describes.

Agent accuracy

Generating a skill locally from the checked-out registry guarantees an agent sees the actual version, not stale published docs.

CLI shape

CommandOutcome
dart run ds_workbench initCreates the initial design_space/, registry, example atoms/components, screens folder, and generated-skill target.
dart run ds_workbench runStarts the interactive Flutter workbench against the repository’s design space; watches changes and opens the selected device target.
dart run ds_workbench generate skillDerives design_space/skills/design-system/SKILL.md from the registry and saved screen examples.
dart run ds_workbench verifyValidates registry rules and runs the configured widget/golden scenarios.

Suggested repository layout

app/ ├── lib/ ├── design_space/ │ ├── atoms/ │ ├── components/ │ ├── layouts/ │ ├── screens/ │ ├── assets/ │ ├── design_space.dart │ └── skills/design-system/SKILL.md └── test/design_space/

The CLI package is infrastructure; design_space/ is product code. Commit the latter. Generated skill output is committed too, so agents and reviewers can see exactly what changed. The runner is never the source of truth.

Component inventory for the first usable system

System components supplied by the tool

  • Registry explorer and search
  • Atom editor/inspector
  • Component catalogue with variant controls
  • Canvas, layers/tree, selection, and property inspector
  • Constrained layout/drop-zone primitives
  • Device, theme, locale, text-scale, and state preview
  • Skill preview/export and validation report

First app-defined components to model

  • Atoms: colour role, text style, spacing, radius, shadow, icon, motion
  • Layout: page, section, row, column, stack, scroll, grid, spacer
  • Input: button, icon button, text field, selection control
  • Content: text, image, card, list row, badge, divider
  • Feedback/navigation: app bar, tabs, navigation bar, dialog, sheet, banner, loader

The tool provides the layout primitives and rails; the app package decides whether its public components are named DsButton, PrimaryButton, or something domain-specific.

Scope

  • A Dart CLI and a Flutter workbench runner.
  • A repository-local registry and declarative screen manifests.
  • Generated global skill with a complete atom/component index and canonical screen examples.
  • Optional component-scoped skill generation later.

Non-goals

  • A proprietary remote source of truth.
  • Requiring a generated Dart file for every exploratory canvas edit on day one.
  • Replacing normal Flutter source review or tests.
  • General app-logic authoring.

Implementation sketch

ds_workbench CLI → discovers design_space/design_space.dart → starts WorkbenchApp → reads Registry → edits screen manifests → renders Flutter preview → derives SKILL.md → verify

Use a simple Dart registry first. Each atom and component registers an ID, name, description, schema, legal slots, variants, preview builder, and source path. Screens are a serializable tree of these IDs. This gives the canvas, skill generator, and validator the same graph.
