Decision concept · showcases

Render real widgets now. Earn a manifest later.

A Showcase should prove how the consumer’s actual components work together. Desy should not invent a second Flutter language merely to describe a demo screen.

Recommendation

Keep widget-returning Showcases as the default composition contract. Add a second, opt-in manifest form only after component IDs, legal slots, and serializable knob values are stable enough to validate it. Do not build a general widget DSL.

Consumer widget builder→Real themed Showcase→Observe repeated structure→Optional typed manifest spike

Reason for existing

Composition evidence

Isolated components do not reveal hierarchy, density, content pressure, or responsive interaction. Showcases provide representative screens for human and automated review.

Consumer fidelity

A normal widget builder can use the app’s real components, theme, layout, localization, and sample state without Desy recreating Flutter.

Future structure

A constrained manifest could later make compositions queryable and editable, but only if it references contracts the registry already owns.

Scope

Keep now

  • DesyShowcase owns a stable ID, name, description, and real widget builder.
  • The Showcase renders beneath the consumer’s active theme.
  • Consumers assemble the demo from production components in normal Dart.
  • Widget tests and golden evidence may exercise the rendered Showcase.

Prototype later

  • A serializable tree containing registered component-instance IDs.
  • Children assigned only to registry-declared legal slots.
  • Values restricted to declared, serializable knob values and sample content.
  • A renderer that resolves the same registry and returns a normal widget to the existing Showcase surface.

Non-goals

  • No generic Row, Column, Stack, padding, colour, or callback vocabulary that shadows Flutter.
  • No serialization of business logic, navigation, services, secrets, or application state.
  • No requirement that a consumer describe an existing screen twice.
  • No generated production widget code in the first release.
  • No assumption that every Showcase must become editable in the canvas.

Implementation sketch

4 · DecideCompare authoring cost, diff quality, migration burden, and agent usefulness.Promote the manifest only if it beats ordinary Dart for a recurring workflow.

Open questions

  • Which three real screens expose enough repeated structure to justify a manifest?
  • Are layout primitives registered consumer components, Desy recipes, or normal Dart that should remain opaque?
  • How are manifest schema versions and component-contract migrations handled in repository history?
  • Should a manifest support only named component instances initially, or also controlled knob overrides?
  • What evidence would prove the manifest helps agents more than a widget builder plus registry metadata?

Do or don’t

Impact 4 / 5Complexity 3 / 5Yield 4 / 5

Do preserve the widget path and run a narrow manifest spike after contracts stabilise. The reward is machine-readable composition without blocking real screens today. Don’t start with a DSL: its 5/5 complexity and source-of-truth risk are not justified while ordinary Dart already renders the required compositions.
