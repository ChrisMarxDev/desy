Rank 12 · Real-widget review

Inspect the real preview without turning Desy into a different authoring system.

Widgetbook validates the value of quick text-scale testing, semantics visualization, selection, zoom, and shareable states. Desy should adopt only the slices that strengthen the Registry Spine: a bounded preview session around the consumer’s real Flutter widget.

Impact 5/5Complexity 5/5Risk 3/5

Reason and user value

Reviewers need to find layout and accessibility defects while a component is already visible. Text scale is immediate, semantics makes the accessibility contract inspectable, and a visual inspector can reduce guesswork during feedback.

Smallest useful slice

Offer resettable preview-environment controls plus a local, scoped visual accessibility overlay. It changes only ephemeral preview state, reads Flutter’s semantics for the real consumer widget, and requires no consumer metadata.

Scope

  • Text scale, direction, bold text, contrast, and reduced-motion controls around the selected real consumer preview, preserving theme and logical preview size.
  • An opt-in overlay that draws semantic labels and actionable hit-target bounds inside that preview boundary: green for targets at least 44 logical pixels, red when smaller, and pink when unlabeled.
  • A compact detail-canvas action bar for zoom, device, inspection, and future share-link controls.
  • Later, a bounded inspector mode for element selection, geometry, and color sampling in consumer preview content.
  • A future share-link contract for validated route, theme, viewport, and typed knob values.

Non-goals

  • No modification or approximation of consumer widgets.
  • No inspection of Desy-owned navigation, panels, or editing chrome.
  • No serialization of callbacks, live Elements, RenderObjects, or arbitrary application state.
  • No hosted accessibility service or automatic remediation.
  • No separate preview catalogue or persisted registry mutation.

Implementation sketch

  1. Define one typed, ephemeral preview-session object with a 1.0 text-scale default and existing route/theme/device selections.
  2. Apply environmental overrides in the current preview wrapper, after the consumer theme has been selected and before presentation scaling.
  3. Give the real preview its own semantics boundary, collect its debug semantics nodes locally, and paint labels and target bounds from that boundary—never from the Desy scaffold.
  4. Keep this visual tool debug/profile-only; use Flutter guideline tests for reliable pass/fail checks.
  5. Add the detail-canvas action bar as Desy-owned shell UI with keyboard-operable controls.
  6. Build later inspector selection atop the existing scoped annotation/targeting boundary, retaining source evidence rather than live widget references.
  7. Only after preview state is validated and versioned, define URL encoding for stable IDs and typed scalar values.

Open questions

  • Which text-scale presets best match practical review work?
  • Does the semantics view visualize only, or surface bounded diagnostics?
  • Can color sampling remain platform-consistent across Flutter targets?
  • How are unknown or stale URL values diagnosed without breaking the preview?
  • Should share links begin as copyable local URLs before any persistence exists?

Acceptance criteria

  • Preview environment controls update the real widget while preserving selected theme, logical size, and registry identity.
  • Semantic labels and hit-target bounds originate only from the consumer preview boundary.
  • Every actionable target is visually classified as pass, undersized, or unlabeled; this remains a review aid rather than a conformance verdict.
  • Reset is deterministic and requires no declaration change.
  • Invalid shared values fail visibly and safely against the current registry.

Do or don’t?

Do text scale after the detail action-bar seam exists; prototype the rest as extensions. The first slice has high value and low declaration burden. Semantics, selection, zoom, sampling, and URL state share a session boundary but have different maturity and platform risks, so they should not land as one oversized core feature.
